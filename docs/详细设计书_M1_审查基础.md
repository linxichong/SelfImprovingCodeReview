# M1 详细设计书：可度量的单代理审查

## 1. 目的与范围

M1 接收 Git 差异，通过确定性验证筛选单个审查角色应用规则后提出的候选，并保存复现信息及费用。范围包括 FN-01～06、FN-08、FN-09、FN-11、FN-13、FN-17 的基础和 FN-18 的骨架。

M1 不包含记忆注入、动态上下文获取工具、自我验证实际处理和 SCM 发布。自我验证关闭时返回 `REFLECTION_SKIPPED`，上下文不足时返回 `NEEDS_CONTEXT`。

## 3. 输入契约

~~~python
@dataclass(frozen=True)
class ReviewRequest:
    repository_path: Path
    project_id: ProjectId
    diff_source: DiffSource
    mode: ReviewMode
    output_path: Path | None
    config_path: Path | None


class DiffSourceKind(Enum):
    WORKSPACE = "workspace"
    RANGE = "range"
    COMMIT = "commit"
    FILE = "file"
~~~

`diff_source` 必须且只能指定一种来源。仓库根目录须与 `git rev-parse --show-toplevel` 的结果一致。使用参数列表执行 Git 命令，禁止 Shell 展开。

## 4. 领域模型

| 模型 | 字段及约束 |
|---|---|
| `ChangedLine` | 变更前后的行、类型、文本、`is_commentable` |
| `DiffHunk` | 变更前后的范围、头部、ChangedLine 元组 |
| `ChangedFile` | 变更前后的路径、变更类型、语言、差异块、二进制标志 |
| `FileDecision` | `REVIEW/FILTER/LIGHTWEIGHT`、原因代码 |
| `ReviewBundle` | ID、文件、风险、适用规则 ID |
| `ReviewPlan` | 审查角色类型、预算、自我验证禁用 |
| `CandidateFinding` | LLM 返回的结构化候选 |
| `Finding` | 已赋予确定性 ID、指纹和验证结果的候选 |

集合使用不可变元组，时间统一为 UTC，路径使用 `NormalizedPath`。

## 5. 获取及解析差异

| 输入源 | 对应 Git 命令 |
|---|---|
| 工作树 | `git diff --no-ext-diff --unified=3 --binary` |
| 范围 | `git diff --no-ext-diff --unified=3 <base>...<head>` |
| 提交 | `git show --format= --no-ext-diff --unified=3 <sha>` |
| 文件 | 以 UTF-8 读取指定补丁，强制大小上限 |

使用 `git rev-parse --verify` 验证修订。按以下顺序解析。

1. 对每个 `diff --git` 头部开始一个文件，读取重命名、添加、删除和二进制元数据。
2. 解析差异块头部 `@@ -old_start,old_count +new_start,new_count @@`。
3. 上下文行计入变更前后双方，删除行只计入变更前，新增行只计入变更后。
4. 在差异块末尾比对实际行数与头部声明的数量。
5. 不匹配、越界、NUL 和仓库外路径均抛出 `InvalidDiffError`。

只有新增行设置为 `is_commentable=true`，审查发现范围必须包含至少一行新增行。

## 6. 文件筛选与简单审查单元划分

筛选原因代码为 `BINARY`、`GENERATED`、`LOCK_FILE`、`VENDOR`、`BUILD_OUTPUT`、`MINIFIED`、`EXCLUDED`。判定结果保存在运行记录中。

M1 审查单元划分

1. 将生产文件与具有相同主文件名或匹配配置模式的测试放在同一审查单元。
2. 将模式、迁移和同一目录下的变更归入同一候选单元。
3. 对关联不明的文件，每个文件单独划分一个审查单元。
4. 超过 8,000 Token 时，先按文件边界拆分，再按差异块边界拆分。
5. 单个差异块本身超限时，以 `BUDGET_EXCEEDED` 记为参考内容，禁止发送给 LLM。

## 7. 规则与执行计划

按路径升序读取 `config/rules/**/*.yaml` 的规则 YAML，拒绝未知字段、重复 ID、空适用范围和未知严重程度。已指定的范围组之间取逻辑与，组内取逻辑或。`paths` 使用匹配规范化相对路径的 glob，`keywords` 匹配新增行并区分大小写。排序为 `severity desc, id asc`。

规则解析为每个文件建立与适用规则 ID 的对应关系。提示词发送正文去重后的规则目录，以及变更元数据中按文件划分的 `applicable_rule_ids`。因 Token 预算未发送的规则 ID 同样从按文件的对应关系中排除。因此，即使同一审查单元包含适用范围各异的实现与测试文件，也能明确每条规则的适用文件。

将各规则的 `path + content_hash` 按路径顺序拼接并计算 SHA-256，作为规则集哈希。空规则集同样创建快照。

| 条件 | 风险 | 审查方向 |
|---|---|---|
| 认证、权限、敏感信息、加密、debug／PROPAGATE_EXCEPTIONS／resolve_entities 等安全配置 | HIGH | 安全 |
| SQL、命令、反序列化、迁移 | HIGH | 安全与数据 |
| API、控制器、模式 | MEDIUM | API 与验证 |
| 只有测试 | LOW | 测试与回归 |
| 其他 | MEDIUM | 通用 |

`review rules check` 不运行 LLM、敏感信息检查及持久化，而针对指定差异运行与正式审查相同的
`RuleLoader`、`RuleMatcher`、`SimpleBundler`、`RuleBasedReviewPlanner` 及规则 Token 预算选择函数。
按文件以 JSON 返回命中规则、命中的 `languages/paths/keywords` 值、未命中的规则、
`failed_scope_groups` 和能否发送至提示词。命中但因预算未发送的规则记为
`RULE_TOKEN_BUDGET_EXCEEDED`。为复现关键词判定与按风险分配的预算，诊断也必须使用
与正式审查相同的差异源，`--file` 仅用于筛选该差异中的一个文件。

M1 的审查角色类型始终为 `GENERAL`。计划处理仅按风险确定规则与预算，无需调用 LLM。`AiGatewayLlmClient` 使用 LiteLLM Python SDK 的 `litellm.completion`，指定 `model=openai/<model>` 和 `base_url=https://aigw.ldjp-ai.link/v1`。通过 `num_retries=0` 禁用 LiteLLM 自身重试，由适配器集中管理有上限的重试。默认省略 `temperature`，只有配置显式指定时才发送。禁止向领域层和应用层暴露网关后端提供商的专有 SDK 及 LiteLLM 专有类型。

安全配置分类依据新增行中的关键词确定性选择审查方向。分类本身不确认漏洞。
`debug=False` 与 `resolve_entities=False` 也作为安全配置变更分到 HIGH，单凭该分类不得生成审查发现。
M1 也将方向设为 security，M3 的角色选择采用同一分类。调用次数和输出 Token 上限保持原值。
自处理版本 0.1.1 起采用该分类与严格的记忆 Scope 匹配，借助包含处理版本的幂等键，
禁止复用 0.1.0 的已完成结果。

| LiteLLM 异常 | 项目异常 | 重试 |
|---|---|---|
| `APIConnectionError`、`Timeout`、`RateLimitError`、`InternalServerError`、`ServiceUnavailableError` | `LlmClientError(is_retryable=True)` | 执行至配置的上限 |
| `APIResponseValidationError` | `InvalidLlmOutputError` | 不执行通信重试。只修复格式 1 次 |
| `AuthenticationError`、`BadRequestError`、其他 `APIError` | `LlmClientError(is_retryable=False)` | 否 |

从 LiteLLM 响应提取单个 JSON 对象后，依据第 9 章的封闭模式重新验证。在 `llm_calls` 记录输入和输出 Token、等待时间、尝试次数及能获取的费用。

更新到 LiteLLM 1.100.4 时，通过测试重新确认现有的请求参数、异常分类和重试、响应解析及用量契约。后续更新 SDK 时也须验证同一契约。

开发和测试可选用 `DatasetLlmClient`。从仓库内受版本管理的 JSON 数据集中返回与请求正文匹配的固定响应，无需获取 API 密钥、获得对外发送权限或连接网络。没有匹配项时使用数据集的默认响应。

## 8. 敏感信息检查与提示词

构建提示词之前，使用严格配置检查每个审查单元的差异。一旦检出任何敏感信息，便将整次运行设为 `BLOCKED`，仅记录文件、行和输入源类型。

提示词依次包含可信系统指令、输出模式、可信规则、不可信元数据及不可信差异。转义边界标记，仅保存版本、哈希及 Token 数，禁止保存完整提示词。

`prompts/candidates/review_general_v1.yaml` 的版本 6 是评估候选，明确要求检查独立变更点，并报告
在不同函数中分别需要独立修复的同类问题。不得仅凭类型或命名假定安全，沿用依据不足时的
`needs_context` 及既有确定性验证。
默认加载器不读取该子目录。固定用例的变更前后实测、正式 B/C 评估和必要的人工裁定完成之前，
禁止以该候选替换默认版本 5。
调查依据和未完成条件见 [P0 调查记录](P0_重大問題退行調査.md)。

`prompts/candidates/v7/review_general_v1.yaml` 的版本 7 作为独立开发候选，
增加逐函数检查输入、处理、使用端和防护，以及明确缺失前提的要求。
安全判断缺乏必要事实时，使用既有模式的 `needs_context=true` 指出需要确认的事项，
禁止转为已确认的主要审查发现或表示已验证安全的空结果。
版本 5 保留为默认，版本 6 留存为历史候选。开发比较以同一模型和配置比较版本 5 与版本 7。
行位置、依据、参考分类的确定性验证及正式验收条件保持原样。

版本 7 的开发比较发现，过短的重复代码引用会产生歧义。因此，
`prompts/candidates/v8/review_general_v1.yaml` 的版本 8 增加输出指令，要求引用重复代码时
包含从目标函数到问题位置的连续新增行。
位置仍由系统通过匹配原文确定，禁止根据 LLM 返回的行号消除歧义。
同时抑制仅通过虚构路径否定明确防护措施的确认请求。保留版本 7 的结果，
版本 8 使用相同的开发输入、模型和配置作为独立实验验证。默认仍为版本 5。

## 9. LLM 输出模式

~~~json
{
  "schema_version": 1,
  "findings": [{
    "file": "src/example.py",
    "start_line": 10,
    "end_line": 10,
    "category": "correctness",
    "issue_type": "null-dereference",
    "rule_id": "PYTHON.NULL_DEREFERENCE",
    "primary_entity": "user",
    "severity": "high",
    "title": "处理 user 可能为 null 的情况",
    "description": "此分支中的值可能为 None。",
    "evidence": {"quote": "user.name", "reason": "执行到此行时，该值可能为 None。"},
    "suggestion": "引用 user 前提前结束处理。",
    "needs_context": false
  }]
}
~~~

通过模式限制审查发现数上限、字符串长度、枚举类型，并禁止额外属性。解析失败时，以同一输入哈希仅请求一次修复。

## 10. 验证与审查管理

按以下顺序验证。

1. 模式。
2. 文件是否存在及是否属于该审查单元。
3. 规则 ID 是否匹配通用审查发现的确定性 ID，或确实发送给目标文件的项目规则 ID。
4. 排除可通过确定性方式证伪的候选。
5. 将依据引文映射到已发送差异中唯一对应的新增行。
6. 验证由依据确定的行范围与新增行存在交集。
7. 生成指纹。
8. 合并重复项。

禁止将模型返回的 `start_line` 和 `end_line` 作为最终位置。单行引文按新增行正文中的子串匹配，
多行引文按连续新增行正文完全匹配。找到唯一结果时，用该范围替代候选行号。
未找到引文时标记为 `EVIDENCE_NOT_IN_PAYLOAD`，匹配多处时标记为 `EVIDENCE_AMBIGUOUS`。
引文可带 Unified Diff 的 `+` 标记，代码正文依原样比对。

对于 Python 的 `SYNTAX_ERROR` 候选，只有能从文件首行开始获取单个差异块中的变更后代码片段时，
才使用 `ast.parse` 证伪。解析成功则以 `PYTHON_SYNTAX_VALID` 排除该候选。
片段不完整或解析失败时，仅凭这项检查不能接受或排除候选。

M1 使用 `reflection_status=REFLECTION_SKIPPED`。`needs_context=true` 归为参考项，排除在主审查发现之外。指纹相同时优先保留严重程度更高的候选，然后比较依据的具体程度，仍相同则按输入顺序保留。

保存前按上述规则合并同一审查单元中具有相同指纹的候选。
结果、单元结果哈希、规则及记忆关联、自我验证审计与各角色采用来源统一使用最终采纳的审查发现 ID。
记录合并前的候选数与验证通过数，并将排除条数记为重复数。重新读取已完成结果时也返回相同结果和统计。
保留数据库指纹唯一约束，禁止通过 SQL 忽略冲突或修改指纹绕过约束。


对于独立于项目规则的审查发现，将 `issue_type` 转为大写，非字母数字字符转成下划线，形成 `GENERAL.<ISSUE_TYPE>`。项目规则不得使用 `GENERAL` 命名空间。模型返回该命名空间时，依据 `issue_type` 确定性地重算并采用。候选返回项目规则 ID 时，依次验证该规则是否存在于规则快照、是否实际构建到提示词、是否适用于目标文件。分别以 `UNKNOWN_RULE_ID`、`RULE_NOT_SENT`、`RULE_NOT_APPLICABLE_TO_FILE` 排除不匹配候选。

当审查单元的 `applicable_rule_ids` 为空时，在系统指令、无规则区块及响应模式三个位置明确禁止
使用项目规则 ID，并要求使用 `GENERAL.<ISSUE_TYPE>`。
当前加强此约束及依据引用格式的审查提示词为 `review_general_v1@5`。

解析或规则引用验证排除候选时，在运行级测量数据中保存候选总数、接受数、排除数以及
按固定原因代码统计的数量。只公开原因代码的计数，禁止保存被排除候选的标题、说明、
路径、证据及原始响应。借此区分模型漏检与模型生成候选后被确定性验证排除。

## 12. 处理时序

~~~mermaid
sequenceDiagram
    participant C as CLI
    participant U as 审查运行
    participant G as Git／差异
    participant R as 规则／审查单元划分
    participant S as 敏感信息检查
    participant L as LLM
    participant V as 验证处理
    participant D as SQLite
    C->>U: 审查请求
    U->>G: 获取并解析差异，执行路径策略和文件筛选
    U->>D: 按幂等键查询已完成结果和恢复候选
    opt 无已完成结果
        U->>R: 划分审查单元并创建执行计划
        U->>D: 保存运行启动或恢复状态及筛选结果
        U->>S: 依次检查未完成单元的输入
        alt 检出敏感信息
            U->>D: 保存被拦截的单元
        else 检查通过
            loop 每个审查单元
                U->>L: 使用经检查的输入执行结构化审查
                U->>V: 验证单元结果
            end
            U->>D: 按顺序保存单元结果及审查发现
        end
        U->>V: 汇总并去重
        U->>D: 保存最终结果
    end
    U-->>C: 审查结果
~~~

一个审查单元失败时，其他审查单元继续执行。检出敏感信息时立即拦截整次运行。

## 13. 输出

JSON 顶层包含 `schema_version`、`run`、`findings`、`reference_findings`、`filtered_files`、`metrics`、`errors`。`metrics` 包含 `candidate_count`、`accepted_candidate_count`、`rejected_candidate_count` 和以固定原因代码为键的 `rejection_reasons`。终端从同一 DTO 格式化显示，文件经临时文件以原子重命名写入。

## 14. 测试方针

M1 测试分为单元、契约、集成、安全和评估。单元测试与集成测试的用例 ID 是稳定标识符，
可通过测试代码、测试结果或缺陷记录追溯。

| 层级 | 对象 | 外部依赖 |
|---|---|---|
| 单元 | 函数、类、分支、输入验证和异常转换 | 使用模拟、测试替身或固定值 |
| 契约 | detect-secrets、LiteLLM、Git、SQLite 的边界契约 | 原则上使用模拟，隔离最低限度的实际处理 |
| 集成 | 从差异解析到 SQLite 保存及 JSON 结果输出的处理基础 | Git 和 SQLite 使用临时空间，LLM 使用固定数据集或可控测试替身 |
| 安全 | 提示词注入、禁止路径、发送前拦截敏感信息且不保存 | 禁止联网 |
| 评估 | 以固定数据验证审查发现、哈希、测量数据的可复现性 | 与常规测试分开 |

测试涵盖正常路径、边界值、无效输入、依赖故障及重试。时间、UUID、随机数、LLM 响应与网络
须可控制，禁止依赖执行顺序及运行环境。

## 15. 单元测试规格书

### 15.1 目的与范围

单元测试验证 M1 各处理单元能独立于外部服务按规格作出判定，失败时返回已定义的异常或结果。
测试代码放在 `tests/unit/`。

单元测试需达到 100% 覆盖的范围为无需外部资源即可按处理单元验证的领域处理、配置、解析、
筛选、划分、计划、构建、验证、汇总与输出转换。真实 Git、真实 SQLite、LiteLLM、
detect-secrets、CLI 进程边界及编排它们的用例由契约、集成与 E2E 测试验证。
禁止只为提高覆盖率而把同一处理重复纳入单元测试。

M1 整体合并单元、契约、集成与 E2E 的覆盖率，范围为
`src/self_improving_code_review/**/*.py` 的全部可执行代码。
`cli/`、`application/`、`domain/`、`infrastructure/`、`security/` 均纳入 M1 整体覆盖率。

### 15.2 覆盖率验收标准

M1 采用以下严于开发标准通用下限的完成条件。

| 指标 | 必需值 | 判定 |
|---|---:|---|
| 单元测试范围的语句覆盖率（C0） | 100% | 验证适合单元测试的各处理单元中的全部可执行语句 |
| 单元测试范围的分支覆盖率（C1） | 100% | 验证同一范围内条件分支、短路求值及异常分支的全部路径 |
| M1 整体语句覆盖率（C0） | 100% | 合并单元、契约、集成和 E2E 测试后，未执行语句数为 0 |
| M1 整体分支覆盖率（C1） | 100% | 合并上述测试后，部分覆盖的分支数为 0 |
| 测试通过率 | 100% | 不得留下失败、意外跳过或 `xfail` |

单元测试与 M1 整体门禁的标准执行命令如下。

~~~bash
uv run --frozen pytest tests/unit -q

uv run --frozen pytest -q \
  --cov=self_improving_code_review \
  --cov-branch \
  --cov-report=term-missing \
  --cov-report=xml:coverage.xml \
  --cov-fail-under=100
~~~

除了确认 `--cov-fail-under=100` 成功，还应从报告确认语句覆盖率（C0）和分支覆盖率（C1）
分别达到 100%。四舍五入后显示为 100% 的值不予通过。

原则上禁止通过 `# pragma: no cover`、`omit` 或 `exclude_lines` 排除代码。
若须排除无法执行的平台专有分支等内容，应在设计书与拉取请求中记录理由、目标行、替代验证和质量影响，
并经审查人员批准。禁止仅为达到 100% 而进行无意义调用、吞掉异常或使用不检查实际值的表面断言。

### 15.3 共通测试条件

| 项目 | 条件 |
|---|---|
| 运行环境 | 由 `pyproject.toml` 和 `uv.lock` 固定的 Python 3.12 及更高版本环境 |

| 时间与 ID | 注入固定时钟与固定 UUID 生成器 |

### 15.5 用例设计规定与证据

- 为每个公开函数、方法和类列出适用的正常、边界、无效、依赖异常路径。

### 16.4 验证项目

每个集成用例均须直接验证以下内容。

1. `review_runs`、`bundles`、`bundle_files`、`findings`、`rule_snapshots`、
   `rule_snapshot_items`、`finding_rules`、`llm_calls` 的数量、外键、状态和测量值。
