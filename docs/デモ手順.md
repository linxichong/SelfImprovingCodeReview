# GitHub PR 审查与知识复用演示

使用虚构订单服务的 [PR #1「Demo/sql lookup」](https://github.com/linxichong/code-review-demo/pull/1)。
使用外部 LLM 审查，从 GitHub 回复中提取知识候选，再用维护人员批准的知识重新审查同一个 PR。

[演示问答](デモ_QA.md)介绍上下文构建、业务规则、知识审批和复用，以及如何解读结果。

## 在 VS Code 中复用知识

用 VS Code 打开 WSL 中的 SelfImprovingCodeReview。在 Codex 里选择 $self-improving-code-review，
在 GitHub Copilot Chat 里选择 /self-improving-code-review。告知工具目标 PR、当前演示会话的配置文件路径，
以及是否允许发送到外部 LLM，并要求它完成审查、反馈、知识审批和重新审查。
在运行 CLI 的环境中设置凭据。

Skill 会先试运行 PR 审查并给出反馈建议。负责人确认后，通过本地 CLI 登记反馈。
知识候选需要单独审批。批准后，用知识重新审查，并核对实际使用的知识 ID 和版本。
如需演示 GitHub 发帖和回复同步，请使用下列步骤。
[Skill 的知识复用步骤](../.agents/skills/self-improving-code-review/references/feedback-to-memory.md)

<a id="chat-から認証情報を利用できない場合"></a>

### Chat 无法使用凭据时

VS Code Chat 启动 CLI 的环境可能与用户操作的 WSL Bash 不同。
可分别在设置凭据的 Bash 和 Chat 启动 CLI 的环境中运行以下命令。
命令只显示变量名和设置状态。scm review 需要 PAT，ai_gateway 审查和候选提取需要 API 密钥。

```bash
uv run --frozen python -c 'import os; print({name: bool(os.environ.get(name)) for name in ("REVIEW_SCM_TOKEN", "REVIEW_LLM_API_KEY")})'
```

如果 Chat 环境未收到必要的变量，请告知它「需要外部通信的命令由我在已设置凭据的 WSL 终端执行」。
在设置了凭据的同一个 Bash 中运行 Skill 给出的命令。初次和再次审查后，
告知 Skill 结果 JSON 的保存位置。提取候选后，提供 candidate_status 和 candidate_memory_id。
凭据应留在终端环境。可以在 Chat 中查看候选，并在负责人确认后执行本地知识审批。

<a id="事前準備"></a>

## 前置准备

确认 PR #1 处于 Open 状态，base 是 main，head 是 demo/sql-lookup。
如果 PR 未合并且处于 Closed 状态，请在 Conversation 标签页选择 Reopen pull request。
PR 恢复 Open 后执行步骤 1。切换演示会话时也保持 PR 打开。
使用 linxichong 的
[细粒度 PAT](https://github.com/settings/personal-access-tokens/new) 发布审查评论。
在 Resource owner 中选择 linxichong，在 Repository access 的 Only select repositories 中选择
code-review-demo，将 Pull requests 权限设为 Read and write。
使用与发帖者不同的 GitHub 账号回复反馈。

进入 SelfImprovingCodeReview 根目录，后续命令在同一个 WSL Bash 中执行。
DEMO_TOOL_ROOT 是运行 uv run 的工具根目录。DEMO_REPO 是 --repository 指定的
linxichong/code-review-demo 本地克隆。

```bash
DEMO_TOOL_ROOT="$(pwd -P)"
DEMO_REPO="$DEMO_TOOL_ROOT/.review/github-demo/code-review-demo"
printf 'DEMO_TOOL_ROOT=%q\nDEMO_REPO=%q\n' "$DEMO_TOOL_ROOT" "$DEMO_REPO"
```

准备本地克隆，同步 main，并复制工具的提示词资源。确认最后显示的
Git 根目录与 DEMO_REPO 一致。如果中途失败，
解决原因后再创建配置。

```bash
(
  set -e
  test -f "$DEMO_TOOL_ROOT/src/self_improving_code_review/cli/main.py"
  if [ ! -d "$DEMO_REPO/.git" ]; then
    mkdir -p "$(dirname "$DEMO_REPO")"
    git clone https://github.com/linxichong/code-review-demo.git "$DEMO_REPO"
  fi
  git -C "$DEMO_REPO" fetch origin
  git -C "$DEMO_REPO" switch main
  git -C "$DEMO_REPO" merge --ff-only origin/main
  mkdir -p "$DEMO_REPO/prompts"
  cp "$DEMO_TOOL_ROOT/prompts/review_general_v1.yaml" \
    "$DEMO_TOOL_ROOT/prompts/memory_extraction_v1.yaml" "$DEMO_REPO/prompts/"
  git -C "$DEMO_REPO" rev-parse --show-toplevel
)
```

<a id="デモ回を選ぶ"></a>

### 选择演示会话

从头演示时留空，创建新会话。配置、SQLite 和输出保存在
$DEMO_REPO/.review/demo-runs/ 下的各会话目录。请记下显示的 DEMO_SESSION_ID。
从中途恢复或重新打开终端时，使用相同版本的工具执行准备步骤，并输入同一个 ID。
如果选择失败，重新执行下方命令块。

```bash
unset DEMO_SESSION_DIR DEMO_CONFIG DEMO_DB_PATH
DEMO_SESSIONS="$DEMO_REPO/.review/demo-runs"
read -rp '演示会话 ID（按 Enter 新建）: ' DEMO_SESSION_ID && {
  if [[ -z "$DEMO_SESSION_ID" ]]; then
    mkdir -p "$DEMO_SESSIONS" &&
      DEMO_SESSION_DIR="$(mktemp -d "$DEMO_SESSIONS/run-XXXXXXXX")" &&
      DEMO_SESSION_ID="${DEMO_SESSION_DIR##*/}"
  elif [[ "$DEMO_SESSION_ID" =~ ^run-[A-Za-z0-9]{8}$ &&
          -d "$DEMO_SESSIONS/$DEMO_SESSION_ID" ]]; then
    DEMO_SESSION_DIR="$DEMO_SESSIONS/$DEMO_SESSION_ID"
  else
    printf '%s\n' '找不到指定的演示会话。' >&2
    false
  fi
} && {
  DEMO_CONFIG="$DEMO_SESSION_DIR/github.yaml"
  DEMO_DB_PATH=".review/demo-runs/$DEMO_SESSION_ID/github.db"
  printf 'DEMO_SESSION_ID=%s\nDEMO_CONFIG=%q\nDEMO_DB_PATH=%q\n' \
    "$DEMO_SESSION_ID" "$DEMO_CONFIG" "$DEMO_DB_PATH"
}
```

继续之前版本创建的会话时，使用原会话的 DEMO_CONFIG 及其 database.path。
将该 database.path 设为 DEMO_DB_PATH，将配置文件所在目录设为 DEMO_SESSION_DIR。

### 准备配置和凭据

DEMO_CONFIG 尚未创建时，运行下方命令块。恢复会话时使用已保存的配置。
如果回复者账号尚未确定，可以先留空并开始审查。执行步骤 2 前，
在同一个会话中再次运行此配置块，登记回复者。

```bash
read -rp '反馈负责人的 GitHub 用户名（未确定时按 Enter）: ' DEMO_FEEDBACK_LOGIN
DEMO_FEEDBACK_MAPPING='{linxichong725: demo-reviewer}'
if [[ -n "$DEMO_FEEDBACK_LOGIN" ]]; then
  if [[ "$DEMO_FEEDBACK_LOGIN" =~ ^[A-Za-z0-9]([A-Za-z0-9-]{0,37}[A-Za-z0-9])?$ &&
        "${DEMO_FEEDBACK_LOGIN,,}" != linxichong ]]; then
    DEMO_FEEDBACK_MAPPING="{\"$DEMO_FEEDBACK_LOGIN\": demo-reviewer}"
  else
    printf '%s\n' '正在创建审查配置。执行步骤 2 前，请登记与 linxichong 不同的 GitHub 用户名。' >&2
  fi
fi
cat > "$DEMO_CONFIG" <<YAML
schema_version: 1
project_id: order-desk-demo
database:
  path: $DEMO_DB_PATH
llm:
  provider: ai_gateway
  base_url: https://aigw.ldjp-ai.link
  model: gpt-5.6-luna
review:
  mode: rules
memory:
  is_injection_enabled: true
  maintainers: [demo-maintainer]
security:
  allow_external_source: true
scm:
  enabled: true
  provider: github
  repository_external_id: linxichong/code-review-demo
  bot_actor_external_id: linxichong
  publish_enabled: true
  feedback_sync_enabled: true
  feedback_actor_mapping: $DEMO_FEEDBACK_MAPPING
YAML
```

共享屏幕之前，在环境变量中设置 GitHub PAT 及网关 API 密钥。

```bash
read -rsp 'GitHub Token: ' REVIEW_SCM_TOKEN
printf '\n'
read -rsp 'LLM API Key: ' REVIEW_LLM_API_KEY
printf '\n'
export REVIEW_SCM_TOKEN REVIEW_LLM_API_KEY
```

<a id="1-外部-llm-でレビューしgithub-に投稿する"></a>

## 1. 使用外部 LLM 审查并发布到 GitHub

在 PR 的 Files changed 中打开 src/order_repository.py，查看邮箱查询逻辑。
试运行后确认 run.status 为 success，并展示 findings、行内评论计划和输入输出 Token。

```bash
uv run --frozen review scm review --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1 --output "$DEMO_SESSION_DIR/pr-1-dry-run.json" &&
  cat "$DEMO_SESSION_DIR/pr-1-dry-run.json"
```

确认计划后，沿用同一演示会话的配置和 PR SHA 发帖。新会话发帖前，
确认上次演示的评论已清理。如果仍有评论，可以恢复上次演示会话，
或请演示负责人清理旧评论后再发帖。

```bash
uv run --frozen review scm review --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1 --publish
```

确认 scm.publications 的 status 为 published，通过 external_comment_url 打开行内评论。
同一会话的评论仍在时可直接执行步骤 2。已创建候选时从步骤 3 恢复，已批准时从步骤 4 恢复。

发帖失败时，查看 scm.publications 的 safe_error_code。遇到 HTTP_403 时，检查 PAT 的目标仓库、
Pull requests 写权限及仓库限制。如果重新创建了 PAT，
在同一个 Bash 中重设 REVIEW_SCM_TOKEN，并在原演示会话中重试发帖。
遇到 HTTP_422 时，检查 PR 的最新 SHA 与计划发布的行内评论位置。

如果手动删除旧评论，演示会话的 SQLite 仍会保留评论 ID。发布结果为 failed 并显示
已保存的 ID 时，请在 GitHub 核对对应评论。如果要重新发布被删除的评论，
先[新建演示会话](#选择演示会话)，再创建配置并从步骤 1 开始。
原 SQLite 会保留，新会话需要重新登记反馈和知识。

<a id="2-github-の返信から外部-llm-で知識候補を作る"></a>

## 2. 从 GitHub 回复中提取知识候选

使用准备阶段指定的另一个 GitHub 账号，**回复 SQL 注入的行内评论**，输入以下一行。

```text
/review-feedback true-positive --reason "订单查询将邮箱地址视为外部输入。请报告直接拼接 SQL 字符串的问题，并检查是否采用占位符与独立参数。"
```

同步会保存反馈，并调用同一个外部 LLM 提取候选。检查 processed_count，再查看待审批候选。

```bash
uv run --frozen review scm sync-feedback --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1

uv run --frozen review memory list --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --status pending
```

回复处理成功后，提取仍可能失败。请先确认 pending 列表中出现候选。
如果在登记回复者之前同步导致回复被忽略，登记后向同一行内评论发送新回复，再同步。

<a id="3-保守担当者が候補を確認して承認する"></a>

## 3. 维护人员确认并批准候选

在列表中选择目标 memory_id，核对事实、下次审查的关注点、适用范围和依据。
本例根据邮箱查询的事实，判断该关注点能否用于检查订单查询如何将外部输入传给 SQL。

```bash
read -rp 'Memory ID: ' DEMO_MEMORY_ID
uv run --frozen review memory show "$DEMO_MEMORY_ID" \
  --repository "$DEMO_REPO" --config "$DEMO_CONFIG"
```

确认可复用后，将作用范围限定为能在 PR 新增行中确认的文件和函数。
keywords 用于匹配新增行中的文本，risk_tags 用于匹配审查风险级别或关注点。
使用详情中的当前 lock_version 和适用范围批准候选，确认 status 变为 active。

```bash
DEMO_SCOPE="$DEMO_SESSION_DIR/order-email-scope.yaml"
cat > "$DEMO_SCOPE" <<'YAML'
languages: [python]
paths: [src/order_repository.py]
symbols: [find_by_email]
YAML
read -rp 'Lock version: ' DEMO_LOCK_VERSION
uv run --frozen review memory approve "$DEMO_MEMORY_ID" \
  --repository "$DEMO_REPO" --config "$DEMO_CONFIG" \
  --actor demo-maintainer --lock-version "$DEMO_LOCK_VERSION" \
  --scope-file "$DEMO_SCOPE" \
  --reason "此关注点可用于订单查询，且已核实依据和适用范围。"
```

要修改有效版本的适用范围，请用启用了记忆生命周期的维护配置执行 memory archive 和
memory restore。核对恢复后的待批准版本的 lock_version，按上述步骤指定适用范围并批准。

<a id="4-承認済みの知識で同じ-pr-を再レビューする"></a>

## 4. 使用已批准的知识重新审查同一个 PR

以 memory 模式重新审查同一个 PR。查看结果的 run.versions.memory_snapshot_id，
以及该快照中的知识 ID 和版本。

```bash
DEMO_RESULT="$DEMO_SESSION_DIR/pr-1-memory.json"
uv run --frozen review scm review --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1 --mode memory --output "$DEMO_RESULT" &&
cat "$DEMO_RESULT" &&
python3 - "$DEMO_REPO/$DEMO_DB_PATH" "$DEMO_RESULT" "$DEMO_MEMORY_ID" <<'PY'
import json
import sqlite3
import sys
from contextlib import closing
from pathlib import Path

db, result, memory_id = sys.argv[1:]
run = json.loads(Path(result).read_text(encoding="utf-8"))["run"]
if run["status"] != "success":
    sys.exit("请检查重新审查结果的 errors。")
snapshot = run["versions"]["memory_snapshot_id"]
with closing(sqlite3.connect(Path(db).resolve().as_uri() + "?mode=ro", uri=True)) as connection:
    items = connection.execute(
        "SELECT memory_id, version FROM memory_snapshot_items "
        "WHERE memory_snapshot_id = ? AND memory_id = ?",
        (snapshot, memory_id),
    ).fetchall()
if not items:
    sys.exit("目标知识未应用于本次差异，请检查候选的 scope。")
for used_memory_id, version in items:
    print(f"已使用的知识: {used_memory_id} (version {version})")
PY
```

结束后清除当前 Shell 中的凭据。保留用于恢复的会话 ID 和对应目录。

```bash
unset REVIEW_LLM_API_KEY REVIEW_SCM_TOKEN
```
