# GitHub PR のレビューと知識の再利用デモ

架空の注文サービスの [PR #1「Demo/sql lookup」](https://github.com/linxichong/code-review-demo/pull/1) を使う。
外部 LLM でレビューし、GitHub の返信から知識候補を作る。保守担当者が承認した知識を同じ PR の再レビューに適用する。

[デモ想定問答](デモ_QA.md)で、コンテキストの組み立て、業務ルール、知識の承認と再利用、実行結果の見方を確認できる。

## VS Code で知識再利用を進める場合

WSL 側の SelfImprovingCodeReview を VS Code で開き、Codex では `$self-improving-code-review`、
GitHub Copilot Chat では `/self-improving-code-review` を選ぶ。対象 PR、使用するデモ回の設定ファイルの実パス、
外部 LLM への送信可否を伝えて、「レビューからフィードバック、知識の承認と再レビューまで進める」と依頼する。
認証情報は CLI を実行する環境に設定する。

Skill は PR のドライランを実行してフィードバック案を提示する。担当者が案を確認した後にローカル CLI で登録し、
抽出候補の承認は別に確認する。承認後は知識を使った再レビューと適用 ID・版の確認へ進む。
GitHub 上の投稿と返信の同期を実演する場合は、下記の手順を使う。
[Skill の知識再利用手順](../.agents/skills/self-improving-code-review/references/feedback-to-memory.md)

### Chat から認証情報を利用できない場合

VS Code の Chat が起動する CLI と、利用者が操作している WSL の Bash は別の実行環境になることがある。
下記の事前準備で認証情報を入力した Bash と、Chat が CLI を起動する環境で、必要に応じて次のコマンドを実行する。
変数名と設定有無だけを表示する。`scm review` には PAT が必要で、`ai_gateway` でのレビューと候補抽出には API キーが必要。

```bash
uv run --frozen python -c 'import os; print({name: bool(os.environ.get(name)) for name in ("REVIEW_SCM_TOKEN", "REVIEW_LLM_API_KEY")})'
```

Chat 側に必要な値が渡らない場合は、「外部通信が必要なコマンドは、私が認証済みの WSL 端末で実行する」
と伝える。Skill が示すコマンドを、認証情報を設定した同じ Bash で実行する。初回レビューと再レビューでは
結果 JSON の保存先を伝え、候補抽出後は `candidate_status` と `candidate_memory_id` を伝えて続ける。
Chat には認証情報を入力しない。候補の表示や、担当者の確認後に行うローカルの知識承認は Chat 側から進められる。

## 事前準備

PR #1 の状態が `Open` であることを確認する。base は `main`、head は `demo/sql-lookup`。
未マージで `Closed` の場合は、PR の **Conversation** タブで **Reopen pull request** を選び、
`Open` になってから手順 1 を実行する。デモ回を切り替えるときも PR は開いたままにする。
レビューコメントの投稿には `linxichong` の
[fine-grained PAT](https://github.com/settings/personal-access-tokens/new) を使う。
`Resource owner` で `linxichong`、`Repository access` の `Only select repositories` で
`code-review-demo` を選び、`Pull requests` を `Read and write` に設定する。
フィードバックの返信には、投稿者と別の GitHub アカウントを用意する。

SelfImprovingCodeReview のルートに移動し、以降は同じ WSL の Bash で実行する。
`DEMO_TOOL_ROOT` は `uv run` を実行するツールのルート。`DEMO_REPO` は `--repository` で指定する
`linxichong/code-review-demo` のローカルクローン。

```bash
DEMO_TOOL_ROOT="$(pwd -P)"
DEMO_REPO="$DEMO_TOOL_ROOT/.review/github-demo/code-review-demo"
printf 'DEMO_TOOL_ROOT=%q\nDEMO_REPO=%q\n' "$DEMO_TOOL_ROOT" "$DEMO_REPO"
```

クローンを準備して `main` を同期し、ツール側のプロンプト資源をコピーする。最後に表示される
Git ルートが `DEMO_REPO` と一致することを確認する。処理が途中で失敗した場合は、
原因を解消してから設定作成へ進む。

```bash
(
  set -e
  test -f "$DEMO_TOOL_ROOT/src/self_improving_code_review/cli/main.py"
  if [ ! -d "$DEMO_REPO/.git" ]; then
    mkdir -p "$(dirname "$DEMO_REPO")"
    git clone https://github.com/linxichong/code-review-demo.git "$DEMO_REPO"
  fi
  git -C "$DEMO_REPO" fetch origin
  git -C "$DEMO_REPO" switch main
  git -C "$DEMO_REPO" merge --ff-only origin/main
  mkdir -p "$DEMO_REPO/prompts"
  cp "$DEMO_TOOL_ROOT/prompts/review_general_v1.yaml" \
    "$DEMO_TOOL_ROOT/prompts/memory_extraction_v1.yaml" "$DEMO_REPO/prompts/"
  git -C "$DEMO_REPO" rev-parse --show-toplevel
)
```

### デモ回を選ぶ

最初から実演する場合は入力を空欄にし、新しいデモ回を作る。設定、SQLite、出力は
`$DEMO_REPO/.review/demo-runs/` の回別ディレクトリに保存する。表示された `DEMO_SESSION_ID` を控える。
途中から再開する場合やターミナルを開き直した場合は、同じツール版で事前準備を行い、同じ ID を入力する。
選択に失敗した場合はこのブロックをやり直す。

```bash
unset DEMO_SESSION_DIR DEMO_CONFIG DEMO_DB_PATH
DEMO_SESSIONS="$DEMO_REPO/.review/demo-runs"
read -rp 'デモ回 ID（新規は Enter）: ' DEMO_SESSION_ID && {
  if [[ -z "$DEMO_SESSION_ID" ]]; then
    mkdir -p "$DEMO_SESSIONS" &&
      DEMO_SESSION_DIR="$(mktemp -d "$DEMO_SESSIONS/run-XXXXXXXX")" &&
      DEMO_SESSION_ID="${DEMO_SESSION_DIR##*/}"
  elif [[ "$DEMO_SESSION_ID" =~ ^run-[A-Za-z0-9]{8}$ &&
          -d "$DEMO_SESSIONS/$DEMO_SESSION_ID" ]]; then
    DEMO_SESSION_DIR="$DEMO_SESSIONS/$DEMO_SESSION_ID"
  else
    printf '%s\n' '指定したデモ回が見つかりません。' >&2
    false
  fi
} && {
  DEMO_CONFIG="$DEMO_SESSION_DIR/github.yaml"
  DEMO_DB_PATH=".review/demo-runs/$DEMO_SESSION_ID/github.db"
  printf 'DEMO_SESSION_ID=%s\nDEMO_CONFIG=%q\nDEMO_DB_PATH=%q\n' \
    "$DEMO_SESSION_ID" "$DEMO_CONFIG" "$DEMO_DB_PATH"
}
```

以前の手順で開始した回を続ける場合は、その回の `DEMO_CONFIG` と設定の `database.path` を使う。
`DEMO_DB_PATH` にはその `database.path` を、`DEMO_SESSION_DIR` には設定ファイルがあるディレクトリを指定する。

### 設定と認証情報を用意する

`DEMO_CONFIG` が未作成の場合は次のブロックで設定を作る。再開時は保存済みの設定を使う。
返信担当者のログイン名が未定の場合は空欄でレビューを開始できる。手順 2 の前に、
同じデモ回でこの設定ブロックを実行し、返信担当者を登録する。

```bash
read -rp 'フィードバック担当者の GitHub ログイン名（未定なら Enter）: ' DEMO_FEEDBACK_LOGIN
DEMO_FEEDBACK_MAPPING='{linxichong725: demo-reviewer}'
if [[ -n "$DEMO_FEEDBACK_LOGIN" ]]; then
  if [[ "$DEMO_FEEDBACK_LOGIN" =~ ^[A-Za-z0-9]([A-Za-z0-9-]{0,37}[A-Za-z0-9])?$ &&
        "${DEMO_FEEDBACK_LOGIN,,}" != linxichong ]]; then
    DEMO_FEEDBACK_MAPPING="{\"$DEMO_FEEDBACK_LOGIN\": demo-reviewer}"
  else
    printf '%s\n' 'レビュー用の設定を作成します。手順 2 の前に linxichong とは別の GitHub ログイン名を登録してください。' >&2
  fi
fi
cat > "$DEMO_CONFIG" <<YAML
schema_version: 1
project_id: order-desk-demo
database:
  path: $DEMO_DB_PATH
llm:
  provider: ai_gateway
  base_url: https://aigw.ldjp-ai.link
  model: gpt-5.6-luna
review:
  mode: rules
memory:
  is_injection_enabled: true
  maintainers: [demo-maintainer]
security:
  allow_external_source: true
scm:
  enabled: true
  provider: github
  repository_external_id: linxichong/code-review-demo
  bot_actor_external_id: linxichong
  publish_enabled: true
  feedback_sync_enabled: true
  feedback_actor_mapping: $DEMO_FEEDBACK_MAPPING
YAML
```

画面共有の前に、GitHub の PAT とゲートウェイの API キーを環境変数に設定する。

```bash
read -rsp 'GitHub Token: ' REVIEW_SCM_TOKEN
printf '\n'
read -rsp 'LLM API Key: ' REVIEW_LLM_API_KEY
printf '\n'
export REVIEW_SCM_TOKEN REVIEW_LLM_API_KEY
```

## 1. 外部 LLM でレビューし、GitHub に投稿する

PR の **Files changed** で `src/order_repository.py` のメール照会を開く。
ドライランで `run.status` が `success` であることを確認し、`findings`、行コメントの計画、入出力 Token を示す。

```bash
uv run --frozen review scm review --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1 --output "$DEMO_SESSION_DIR/pr-1-dry-run.json" &&
  cat "$DEMO_SESSION_DIR/pr-1-dry-run.json"
```

計画を確認したら、同じデモ回の設定と PR の SHA で投稿する。新規のデモ回では、前回のデモ用コメントが
残っていないことを投稿前に確認する。残っている場合は前回のデモ回を再開するか、デモ担当者が
前回のデモ用コメントを整理してから新規投稿する。

```bash
uv run --frozen review scm review --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1 --publish
```

`scm.publications` の `status` が `published` であることを確認し、`external_comment_url` で行コメントを開く。
同じデモ回のコメントが残っていれば手順 2 へ進む。候補を作成済みなら手順 3、承認済みなら手順 4 から再開できる。

投稿が失敗した場合は `scm.publications` の `safe_error_code` を確認する。`HTTP_403` の場合は PAT の対象リポジトリ、
`Pull requests` の書込み権限、およびリポジトリ側の制限を確認する。PAT を作り直した場合は
同じ Bash で `REVIEW_SCM_TOKEN` を設定し直し、同じデモ回で投稿を再実行する。
`HTTP_422` の場合は PR の最新 SHA と行コメント計画の位置を確認する。

以前のコメントを手動で削除すると、そのデモ回の SQLite にはコメント ID が残る。投稿結果が `failed` で
保存済み ID が表示されたら、GitHub で対象のコメントを確認する。削除済みのコメントに代えて投稿から
やり直す場合は、[デモ回の選択](#デモ回を選ぶ)で新しい回を作り、設定を作成して手順 1 から実行する。
以前の SQLite は保存され、新しい回ではフィードバックと知識を新たに登録する。

## 2. GitHub の返信から外部 LLM で知識候補を作る

事前準備で指定した別の GitHub アカウントで、SQL インジェクションの**行コメントへの返信**に次の 1 行を書く。

```text
/review-feedback true-positive --reason "注文検索ではメールアドレスを外部入力として扱います。SQL 文字列への直接埋め込みを指摘し、プレースホルダーと別引数で渡す実装を確認してください。"
```

同期するとフィードバックが保存され、同じ外部 LLM が候補を抽出する。`processed_count` を確認し、続けて承認待ちの候補を表示する。

```bash
uv run --frozen review scm sync-feedback --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1

uv run --frozen review memory list --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --status pending
```

返信を処理しても候補の抽出が失敗することがあるため、`pending` の一覧で候補が作成されたことを確認してから次へ進む。
登録前に同期して返信が無視された場合は、返信者を登録してから、同じ行コメントに新しい返信を投稿して同期する。

## 3. 保守担当者が候補を確認して承認する

一覧から対象の `memory_id` を選び、事実、次回のレビュー観点、適用範囲、根拠を確認する。
この例では、メール照会の事実を根拠に、注文検索で外部入力を SQL に渡すときの確認観点として使えるかを判断する。

```bash
read -rp 'Memory ID: ' DEMO_MEMORY_ID
uv run --frozen review memory show "$DEMO_MEMORY_ID" \
  --repository "$DEMO_REPO" --config "$DEMO_CONFIG"
```

再利用できると判断した場合は、PR の追加行で確認できるファイルと関数に適用範囲を設定する。
`keywords` は追加行の文字列、`risk_tags` はレビューのリスク水準または観点に照合される。
詳細に表示された現在の `lock_version` と適用範囲を指定して承認し、`status` が `active` になることを確認する。

```bash
DEMO_SCOPE="$DEMO_SESSION_DIR/order-email-scope.yaml"
cat > "$DEMO_SCOPE" <<'YAML'
languages: [python]
paths: [src/order_repository.py]
symbols: [find_by_email]
YAML
read -rp 'Lock version: ' DEMO_LOCK_VERSION
uv run --frozen review memory approve "$DEMO_MEMORY_ID" \
  --repository "$DEMO_REPO" --config "$DEMO_CONFIG" \
  --actor demo-maintainer --lock-version "$DEMO_LOCK_VERSION" \
  --scope-file "$DEMO_SCOPE" \
  --reason "注文検索で再利用できる確認観点であり、根拠と適用範囲を確認した。"
```

有効版の適用範囲を修正する場合は、メモリ生命周期の設定を有効にした保守用設定で `memory archive` と
`memory restore` を実行する。復元した承認待ち版の `lock_version` を確認し、上の手順で適用範囲を指定して承認する。

## 4. 承認済みの知識で同じ PR を再レビューする

同じ PR を `memory` モードで再レビューする。結果の `run.versions.memory_snapshot_id` と、
そのスナップショットに入った知識の ID・版を表示する。

```bash
DEMO_RESULT="$DEMO_SESSION_DIR/pr-1-memory.json"
uv run --frozen review scm review --repository "$DEMO_REPO" \
  --config "$DEMO_CONFIG" --change 1 --mode memory --output "$DEMO_RESULT" &&
cat "$DEMO_RESULT" &&
python3 - "$DEMO_REPO/$DEMO_DB_PATH" "$DEMO_RESULT" "$DEMO_MEMORY_ID" <<'PY'
import json
import sqlite3
import sys
from contextlib import closing
from pathlib import Path

db, result, memory_id = sys.argv[1:]
run = json.loads(Path(result).read_text(encoding="utf-8"))["run"]
if run["status"] != "success":
    sys.exit("再レビューの errors を確認してください。")
snapshot = run["versions"]["memory_snapshot_id"]
with closing(sqlite3.connect(Path(db).resolve().as_uri() + "?mode=ro", uri=True)) as connection:
    items = connection.execute(
        "SELECT memory_id, version FROM memory_snapshot_items "
        "WHERE memory_snapshot_id = ? AND memory_id = ?",
        (snapshot, memory_id),
    ).fetchall()
if not items:
    sys.exit("対象の知識は今回の差分に適用されませんでした。候補の scope を確認してください。")
for used_memory_id, version in items:
    print(f"使用した知識: {used_memory_id} (version {version})")
PY
```

終了時は認証情報をシェルから解除する。再開に使うデモ回 ID と回別ディレクトリは保管する。

```bash
unset REVIEW_LLM_API_KEY REVIEW_SCM_TOKEN
```
