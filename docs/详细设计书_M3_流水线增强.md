# M3 详细设计书：评审处理基础设施增强

## 1. 目的与范围

M3 保留 M1/M2 的外部契约和已保存的数据，增加以下功能。

- 根据变更文件之间的关系确定性地划分审查单元
- 为单个代理按风险选择评审类型
- 在预算、路径策略和敏感信息检查约束下动态获取上下文
- 对通过确定性验证的候选列表执行自我验证
- 使用相同运行 ID 和固定输入按审查单元恢复运行
- 安全并行执行审查单元并确定性地聚合结果

启动多个专业评审角色的架构、向量搜索、SCM 发帖和 Web UI 均不在 M3 范围内。
M3 中的计划、路径授权、预算计算、行映射、去重和是否可恢复仍由确定性逻辑处理。

### 1.1 M1/M2 兼容条件

- 保留 `ReviewMode.BASELINE/RULES/MEMORY`，不增加审查模式。
- 默认禁用上下文获取和自我验证。禁用时，保持请求、响应、展示及存储结果与 M1/M2 相同。
- 扩展复用 `ReviewerType.GENERAL/SECURITY/TEST`、`ReflectionStatus`、`ReviewPlan` 和 `ReviewBudget`，避免重复定义。
- baseline 模式不注入项目规则。评审类型仅改变可信提示词中的关注点。
- memory 模式继续基于变更文件查找记忆。动态获取的文件不得扩大记忆适用范围。
- 将发现关联到原始差异中的新增行，禁止关联到动态上下文。继续严格验证位置和依据引用。
- 保持 M1/M2 已有数据库行原样。M3 的变更通过前向迁移追加。

| 上下文读取端口 | 抽象固定修订版和工作树 | `application/ports/context_source.py` |
| 工具实现 | 无需 shell 的受限读取与搜索 | `infrastructure/context_tools/` |

`RunReviewUseCase` 通过构造器注入接收 Bundler、Planner、工具协调器、自我验证和恢复判定。
CLI 组合入口根据配置组装 M3 实现，避免在生产代码中直接实例化。

### 2.1 评审执行职责划分

RunReviewUseCase 负责执行顺序、外部调用与事务边界。
review_identity.py 处理计划、输入和结果的哈希以及是否可恢复，
review_metrics.py 聚合状态与各角色的度量值，
review_source_mapping.py 负责原文差异的选择和敏感信息检测结果的行映射。
这些模块无输入输出副作用，维持现有哈希格式、排序和判定条件。
review_preparation.py 在启动时组装幂等键、版本信息和单元计划。
_acquire_review_input 负责取得差异、判定目标范围、核对固定源码和加载规则，
通过不可变的 PreparedReviewInput 传给后续流程。调用顺序和已配置依赖的选择保持原样。
单元输入与结果使用 bundle_review_models.py 中的不可变模型。
BundleReviewExecutor 接收已配置的依赖，负责调用 LLM、运行受限工具、自我验证和构建失败结果。
该执行器独立于数据库及 Unit of Work，将 LLM 发送相关的格式修复和敏感信息扫描交由现有边界处理。
RunReviewUseCase 继续负责并行上限、停止信号、角色顺序、稳定排序、恢复、租约核对和存储。
review_aggregation.py 负责合并角色结果、检查版本混用和清理受阻结果。
ReviewResultWriter 在同一 Unit of Work 保存已采纳的单元结果和审计记录，
并在同一现有事务中确定最终状态和 FINALIZED 检查点。
在保存单元及最终确定执行状态前检查租约所有权，最终确定统一使用同一个 finished_at。
RunReviewUseCase 负责记忆保存、整体聚合、输出构建及保存的调用顺序。
ReviewRunStarter 负责启动时核对计划，以及保存新建或恢复的运行。
恢复校验不匹配时使用新 ID 重新计划。恢复已有运行时，取得租约后才更新状态。
新运行在保存运行及规则后取得租约，并在核对所有权后保存初始检查点。
通过 StartedReviewRun 传递已启动的运行、计划、筛选结果及恢复来源。
已完成结果的查询和提前返回仍由 RunReviewUseCase 负责。
_scan_review_bundles 保持扫描顺序，首次检测到敏感信息时中止，并在原有边界保存结果。
review_task_preparation.py 仅接收已检查的输入，依次为主要和辅助角色检索记忆并构建输入。
通过 PreparedReviewTasks 返回实际注入的记忆集合和舍弃数量。
检测到敏感信息时传递空目标，不创建角色任务，也不检索记忆。
review_response_generator.py 负责验证结构化响应及格式修复，
维持现有修复文案、次数上限、异常转换以及用量和尝试次数的累加方式。
review_telemetry.py 负责在完成时发送获准属性和汇总后的度量值。
保留观测区间名称、发送顺序、属性、计数、模型和提示词资源。
ReviewResultAccumulator 保留当前运行的结果、计数及记忆关联。
复制恢复来源的集合，分别统计已采纳结果和去重前的发现。
发生阻断时不累加业务发现，保留原有工具与自我验证用量计数。
累加后以相同顺序保存单元。结果排序、最终统计的分母和属性保持原样。
review_scheduler.py 接收分组执行回调，并按审查单元分组。
在同一运行内共享停止信号，将配置上限和分组数的较小值作为工作线程数。
主要和辅助角色的顺序执行由调用方负责，结果按单元序号和角色类别稳定排序。
异常通过 Future.result 传播，禁止将失败转换为正常结果。
本阶段保留现有单元执行和持久化顺序。

## 3. 配置与启用

在 `ReviewConfig` 中增加以下配置。

~~~yaml
review:
  context_tools_enabled: false
  reflection_enabled: false
  max_workers: 1
  max_context_file_bytes: 1048576
  max_tool_results: 20
  dynamic_context_tokens: 6000
  reflection_tokens: 2000
  max_tool_calls: 5
~~~

| 配置 | 约束 | 含义 |
|---|---:|---|
| `context_tools_enabled` | 布尔值 | 允许动态获取上下文 |
| `reflection_enabled` | 布尔值 | 对候选列表执行自我验证 |
| `max_workers` | 1～8 | 并行审查单元数。1 表示顺序执行 |
| `max_context_file_bytes` | 1～2,097,152 | 单文件读取上限 |
| `max_tool_results` | 1～20 | 搜索工具返回的片段数上限 |
| `dynamic_context_tokens` | 0～32,000 | 单个审查单元附加上下文的上限 |
| `reflection_tokens` | 0～16,000 | 单个审查单元自我验证输入的上限 |
| `max_tool_calls` | 0～10 | 单个审查单元的工具请求次数上限 |

当 `context_tools_enabled=true` 时，要求 `dynamic_context_tokens >= 1` 且 `max_tool_calls >= 1`。
当 `reflection_enabled=true` 时，要求 `reflection_tokens >= 256`。标志为 false 时，即使对应预算为正也不执行。
搜索结果上限取工具自身上限与 `max_tool_results` 的较小值。

M3 不增加 CLI 参数，用户通过现有 `--config` 启用功能。
配置值纳入 `AppConfig.content_hash`，有变更时创建独立运行。

## 4. 处理顺序

~~~text
获取并解析差异
→ 固定规则／记忆状态
→ 筛选文件
→ 构建关系图并划分评审单元
→ 评估风险并确定评审类型
→ 检查初始差异中的敏感信息
→ 执行代理轮次（确定候选或返回工具意图）
→ 验证工具意图并执行受限操作
→ 检查工具输出中的敏感信息
→ 补充上下文并进入下一轮
→ 验证响应模式
→ 验证位置、依据与规则引用
→ 自我验证
→ 保存评审单元
→ 整次运行去重并稳定排序
→ 确定最终结果
~~~

外部 LLM 调用和上下文工具执行期间不得持有数据库事务。
执行意图、调用结果与检查点各自通过短事务保存。

## 5. 增强审查单元划分

### 5.1 关系候选

以变更文件为节点，通过以下确定性检测创建无向边候选。

| 关系代码 | 权重 | 检测条件 |
|---|---:|---|
| `IMPLEMENTATION_TEST` | 100 | 按 M1 去除测试词缀后，文件主名相同 |
| `INTERFACE_IMPLEMENTATION` | 90 | interface/protocol/abc 类文件主名与变更中的 import 或符号引用相匹配 |
| `SCHEMA_PROCESSING` | 80 | schema/openapi/graphql 类文件与引用相同主名的处理文件 |
| `MODEL_MIGRATION` | 80 | model 类路径和 migration 类路径的规范化主名相同 |
| `IMPORT_REFERENCE` | 60 | 在 Python 抽象语法树（AST）中，一个变更文件引用另一文件的模块或已定义符号 |
| `SAME_DIRECTORY_STEM` | 20 | 目录相同且规范化主名相同 |

只分析变更文件。Python 语法解析失败时，跳过当前检测器的边，并继续运行其他检测器。
禁止用 LLM 弥补语法解析失败。

同一文件对有多种关系时，只采纳权重最高的关系。
权重相同时以表内顺序为准。禁止创建自环。

### 5.2 构建连通分量

1. 按规范化 POSIX 路径升序排列节点。
2. 按 `weight DESC, left_path ASC, right_path ASC, relation ASC` 排列边。
3. 使用并查集依次处理边。
4. 两端已经属于同一个分量时，不合并，将边设为 `CUT_CYCLE`。
5. 合并后的差异预估 Token 数不超过 `bundle_diff_tokens` 时才合并，将边设为 `SELECTED`。
6. 超过上限时不合并，将边设为 `CUT_BUDGET`。
7. 孤立节点也单独构成一个分量。

各分量内文件按路径升序排列。单个文件超过上限时，按照与 M1 相同的差异块边界切分。
单个差异块也超过上限时，标记为 `BUDGET_EXCEEDED`，并禁止向 LLM 发送。

审查单元按首个路径和首个差异块的起始行排序，再分配 `BundleId.sequence`。
顺序不得依赖差异的输入顺序或并行完成顺序。

### 5.3 哈希

- `bundle_input_hash`：按稳定顺序对路径、变更类型、语言、差异块正文哈希、风险、评审类型、
  适用规则 ID、记忆 ID 和版本、提示词哈希计算哈希。
- `bundle_result_hash`：按稳定顺序对 `bundle_input_hash`、结束状态、最终发现的 fingerprint 和
  `ReflectionStatus` 计算哈希。

复用已完成的审查单元时，重新核对两个哈希。

## 6. 按风险分派

### 6.1 评审类型

根据现有 `RiskAssessment` 与适用规则选择一个 `ReviewerType`。
优先顺序为 `SECURITY > TEST > GENERAL`。

| 评审类型 | 条件 | 原因代码 |
|---|---|---|
| `SECURITY` | RiskLevel 为 HIGH、关注点与安全有关，或适用规则包含 security 分类 | `SECURITY_RISK` / `SECURITY_RULE` |
| `TEST` | 不满足 SECURITY，且审查单元内的所有文件都是测试 | `TEST_ONLY` |
| `GENERAL` | 其他情况 | `GENERAL_DEFAULT` |

同一审查单元既有实现也有测试时，选择 `GENERAL`，并在关注点中补充测试回归检查。
同时满足安全和测试条件时，选择 `SECURITY`。

### 6.2 规则与提示词

按评审类型选择版本受控提示词中的可信区段。
各类型使用相同的最终发现模式、位置验证、依据验证及规则引用验证。

- baseline 模式下，任何评审类型都使用 0 条项目规则。
- rules/memory 模式下，只将符合 M1 适用范围的规则列为候选。
- 评审类型要求的分类仅能提高已适用规则的预算内优先级。
- 禁止将不匹配适用范围的规则作为必选规则添加。

将选定的 `reviewer_type`、`profile_reason_code` 和关注点保存到审查单元。

## 7. 上下文获取契约

### 7.1 不可信意图与内部请求

分别使用不同类型表示 LLM 返回的值和执行需要的可信值。

~~~python
@dataclass(frozen=True, slots=True)
class ToolIntent:
    tool_name: str
    path: str | None
    path_scope: tuple[str, ...]
    query: str | None
    start_line: int | None
    end_line: int | None


@dataclass(frozen=True, slots=True)
class ValidatedToolRequest:
    run_id: RunId
    bundle_id: BundleId
    repository_root: Path
    source_revision: str | None
    tool_name: ContextToolName
    path: NormalizedPath | None
    path_scope: tuple[NormalizedPath, ...]
    query: str | None
    start_line: int | None
    end_line: int | None
    request_hash: str
~~~

`repository_root`、`run_id`、`bundle_id`、`source_revision` 和已许可的上限
仅由协调流程设置。拒绝 LLM 返回的同名值。

### 7.2 固定输入来源

| 差异来源 | 上下文读取 |
|---|---|
| COMMIT / RANGE | 从解析得到的 40 位提交 SHA 对应的 Git 对象中读取 |
| WORKSPACE | 读取工作树，将首次读取的内容哈希固定在同一次运行中 |
| FILE | 从通过下述一致性验证的工作树读取并固定首次读取的内容哈希 |

固定提交复用现有 `RevisionContentReader`。工作树中的每次读取前后均检查文件类型、大小、
解析后的路径与内容哈希。同一路径的哈希在运行期间变化时，以 `SOURCE_CHANGED` 使审查单元失败。

FILE 输入启用动态上下文时，启动处理前通过 Git 反向应用检查及变更行核对，
确认目标差异已体现在工作树中。无法确认时，在调用 LLM 前以 `UNVERIFIED_CONTEXT_SOURCE` 失败，
防止混用不同版本的代码。FILE 输入未启用上下文获取时无需满足该新增条件。

恢复时重新验证过去读取的路径及内容哈希。任一项发生变化时，获取当前差异并启动新运行。
用于恢复的数据禁止保存工具输出正文。

### 7.3 工具

| 工具 | 参数 | 结果上限 |
|---|---|---:|
| `read_file` | path、start_line、end_line | 连续 1～200 行 |
| `get_changed_file` | path | 当前审查单元的 1 个变更文件 |
| `find_symbol` | query、path_scope | 20 处定义位置，每处最多 200 行 |
| `search_code` | query、path_scope | 20 处字面匹配，每处前后各 5 行 |

`get_changed_file` 的 path 限于当前审查单元中的文件。
`read_file` 仅处理真实存在的 UTF-8 普通文件。
M3 的 `find_symbol` 只查找 Python 抽象语法树（AST）中的函数、类及方法定义。
其他语言返回 `UNSUPPORTED_LANGUAGE`。
`search_code` 执行区分大小写的字面搜索，禁止使用正则表达式、shell 或外部搜索命令。

搜索结果按 `path ASC, start_line ASC, end_line ASC` 排序后应用上限。
结果片段包含 path、行范围和正文。正文仅在内存中处理。

### 7.4 路径范围

将 LLM 的 `path_scope` 作为不可信的相对目录候选，每次最多 10 项，每项最多 512 字符。
为空时使用仓库根目录，并继续应用禁止访问、排除、生成产物和外部依赖策略。

协调流程将候选转换为 `NormalizedPath`，仅允许与仓库根目录相交的范围。
拒绝绝对路径、向上级目录移动、NUL、空元素、glob 和解析后指向根目录外的符号链接。

## 8. 工具安全与预算

执行顺序固定如下。

~~~text
验证意图模式
→ 验证参数长度与类型
→ 规范化路径
→ 判定禁止访问／排除
→ 解析符号链接后再次确认仓库根目录边界
→ 核对普通文件、UTF-8 和大小
→ 执行工具
→ 严格检查敏感信息
→ 计量结果 Token 数
→ 核对预算
→ 对不可信数据边界编码
→ 加入下一轮 LLM 的发送内容
~~~

禁止访问的内容至少包括 `.env`、`.git`、`.review`、私钥、凭据、证书、设备文件、二进制、
vendor、`node_modules`、虚拟环境和生成产物。
同时应用配置中的 `security.blocked_paths` 和 `exclude_patterns`。

每个审查单元的默认预算为 5 次调用、6,000 个动态上下文 Token，每次 200 行。
预留执行名额时扣减调用预算。参数无效、重复请求、NOT_FOUND 或工具失败均不退回名额。

结果超过剩余 Token 预算时，不将正文添加到下一轮提示词，并返回 `BUDGET_EXCEEDED`。
禁止截断单个结果正文。结果含多个片段时，按稳定顺序只采纳预算内的完整片段。

检测到敏感信息时，禁止将工具正文、检测到的字符串和下一轮提示词存入缓存、数据库或日志。
仅记录发现来源、工具名称、文件、行和安全的原因代码，并将整次运行标为 `BLOCKED`。
并行处理期间停止发起新的 LLM 调用，禁止保存或显示已在运行中的调用结果。

## 9. 代理工具循环

### 9.1 轮次模式

禁用上下文获取时沿用 M1 的 `review_output_schema_v1`。
启用时采用以下互斥的轮次模式。禁止将 LiteLLM 特有工具类型公开给应用层或领域层。

~~~json
{
  "schema_version": 1,
  "action": "tool-request | final",
  "tool_request": null,
  "findings": []
}
~~~

- `action=tool-request` 要求提供 `tool_request`，`findings` 为空数组。
- `action=final` 要求 `tool_request=null`，findings 遵循 M1 的封闭发现模式。
- 每轮只能请求一个工具。
- 拒绝未知字段、未知工具、超长字符串及条件不一致。

### 9.2 状态转换

1. 首轮只使用初始差异、适用规则和有效记忆。
2. 返回 `final` 时进入候选验证。
3. 返回 `tool-request` 时验证意图并消耗 1 个调用名额。
4. 相同的规范化请求哈希曾出现时返回 `REPEATED_REQUEST`，跳过执行。
5. 成功取得的正文先经过敏感信息检查，再用不可信数据边界包围后加入下一轮。
6. 失败、NOT_FOUND 或预算超限时，仅将无正文的原因代码传给下一轮。
7. 使用完调用名额后，切换到只允许 `final` 的模式。
8. 对仍无法确定的候选设置 `needs_context=true`，送交参考。

仅允许最终结果的一轮仍返回工具请求时执行一次格式修复，修复后仍失败则结束该审查单元并标为失败。
格式修复不消耗工具调用次数，但计入 LLM 的 Token 数、延迟、尝试次数及成本。
无法从网关响应正文提取 JSON 对象时同样执行格式修复。

每轮 LLM 调用保存 `llm_calls.call_kind=review-turn` 与 `turn_index`。
禁止保存完整提示词、完整响应或工具正文。

## 10. 自我验证

### 10.1 对象与处理顺序

自我验证只处理已通过确定性验证的候选发现，并遵循以下固定顺序。

1. 验证最终轮的 JSON 和封闭模式。
2. 按 M1 验证行位置、证据、规则引用、严重程度和差异范围。
3. 为有效候选分配稳定的 `finding_id`。
4. 将审查单元内的目标候选汇总成一次自我验证请求。
5. 验证自我验证响应的模式、数量及 ID 集合。
6. 为每个候选设置自我验证状态并保存。
7. 执行 M1 去重并聚合整次运行。

行位置等确定性验证失败的候选不纳入自我验证。
最终轮已为 `needs_context=true` 的候选直接保存为 `NEEDS_CONTEXT`，禁止进一步推测或纳入自我验证。

### 10.2 自我验证的输入输出

输入仅包括发现 ID、规范化摘要、严重程度、规则 ID、差异内的最小证据，
以及该发现所依赖的已检查上下文的最小片段。
禁止发送工具结果全文、差异全文或发现未引用的额外上下文。
自我验证期间禁止再调用工具。

响应模式如下。

~~~json
{
  "schema_version": 1,
  "results": [
    {
      "finding_id": "f-...",
      "status": "supported | contradicted | needs-context",
      "reason_code": "EVIDENCE_SUFFICIENT"
    }
  ]
}
~~~

`results` 必须恰好包含输入候选的每个 ID 各一次。
拒绝未知 ID、重复 ID、缺失 ID、自由文本理由和未知状态。
`reason_code` 只允许提示词资源中定义的封闭枚举值。

| 响应状态 | 保存的 `reflection_status` | 主结果 |
|---|---|---|
| `supported` | `SUPPORTED` | 纳入 |
| `contradicted` | `CONTRADICTED` | 不纳入，保留审计记录 |
| `needs-context` | `NEEDS_CONTEXT` | 不纳入，送交人工参考 |
| 禁用自我验证 | `REFLECTION_SKIPPED` | 与 M1/M2 相同 |

自我验证响应无效时，只进行一次格式修复。再次无效时将该审查单元标为失败，
禁止将候选标为 `REFLECTION_SKIPPED` 并按成功处理。
自我验证调用保存为 `llm_calls.call_kind=reflection`，并累加输入输出 Token、
总延迟、尝试次数和可获得的成本。

### 10.3 自我验证预算与版本

- 自我验证输入上限为 `reflection_tokens`。
- 超过上限时，以 `REFLECTION_BUDGET_EXCEEDED` 将审查单元标为失败。禁止按候选 ID 稳定顺序
  拆成多个请求。此失败不属于可重试失败，同一次运行不可恢复。
- 自我验证提示词以 `prompts/reflection_v1.yaml` 进行版本管理。
- 提示词版本与内容哈希纳入运行同一性判定、存储信息和评估条件。

## 11. 从中断恢复

### 11.1 恢复单元

以审查单元为恢复粒度。不恢复工具循环中的中间状态。
由于完整工具正文和提示词不持久化，被中断的审查单元从第一轮重新运行。
只复用已完成的审查单元。

在以下阶段保存检查点。

| 阶段 | 保存时机 |
|---|---|
| `DIFF_PARSED` | 完成差异规范化、敏感信息检查并确定输入哈希后 |
| `PLAN_CREATED` | 确定合并计划、角色类型和适用规则后 |
| `BUNDLE_COMPLETED` | 完成审查单元的候选验证、自我验证和持久化后 |
| `FINALIZED` | 稳定地聚合所有单元并确定运行状态后 |

调用外部 LLM 期间不得持有数据库事务。
`BUNDLE_COMPLETED` 与发现、用量、工具审计、自我验证结果和所用记忆版本在同一 Unit of Work 中提交。

### 11.2 恢复条件

仅在满足以下全部条件时可恢复相同的 `run_id`。

- 状态为 `PARTIAL_SUCCESS` 或可重试的 `FAILED`。
- 仓库、基准修订、目标修订和规范化差异哈希一致。
- 配置、模型、提示词、规则包和敏感信息扫描器的版本与哈希一致。
- 合并计划、各个 `bundle_input_hash` 和角色类型一致。
- M2 中有效记忆集合的哈希一致，且已保存已完成单元所使用的记忆版本。
- 固定版本输入的源码 SHA 或工作树输入的首次文件哈希一致。

`SUCCESS` 返回现有结果，无需重新运行。`RUNNING` 按冲突拒绝。
`BLOCKED` 不可恢复，用户移除原因后创建新运行。
任何同一性条件不一致时，保留现有运行并创建新的 `run_id`。

仅处理中断、临时 LLM 故障、格式修复后响应无效和达到重试上限的数据库锁可重试。
无效输入、无效配置、认证或请求无效以及违反策略均不可在同一次运行中重试。

开始恢复时，在短事务内有条件地更新 `PARTIAL_SUCCESS/FAILED -> RUNNING` 并将 `resume_count` 加 1。
更新条数不为 1 时，按与其他进程冲突拒绝。
`started_at` 保留首次开始时间，`finished_at` 只在恢复期间重置为 NULL。

复用已完成的审查单元前验证 `bundle_result_hash`。
未完成或失败的单元从头执行，禁止复用之前的工具请求或 LLM 响应，
以保证恢复过程独立于未保存的不可信正文。

### 11.3 与 M2 评估的一致性

在 M2 对比评估中，禁止将失败或未完成的评审当作 0 条发现评分。
目标用例只要有一项状态不是 `SUCCESS`，评估即标为 `INCOMPLETE_REVIEW_RUNS`，
且不保存对比指标、建议和候选判定。

重新运行时恢复目标评审的 `run_id`，只有全部达到 `SUCCESS` 才确定对比评估。
正式 B/C 评估继续应用 M2 规定的总体样本、相同条件、至少 3 次重复运行及未裁定数为 0 等条件。

## 13. 并行执行

审查单元可在 `max_workers` 限制内并行执行。
默认值为 1，取值为 1 时执行与 M1/M2 相同的顺序处理。

- 仅协调器持有整次运行的可变状态、停止标志和最终聚合结果。
- 向工作线程传递不可变的审查计划、固定版本输入、预算与依赖端口。
- 每个工作线程使用独立的 SQLite 连接与 Unit of Work，禁止共享连接。
- 为 SQLite 设置 WAL、启用外键并使用有限的 `busy_timeout`。
- 数据库锁重试在同一处理内进行且设有上限，超限时审查单元失败。
- 并行前确定 `bundle_id` 和输出顺序，顺序不得依赖完成先后。
- 最终按路径、行、严重程度和发现 ID 的稳定顺序聚合。

任一工作线程检测到敏感信息时，协调器设置停止标志。
取消尚未开始的工作线程，禁止发起新的 LLM 调用。可以等待已发出的外部调用结束，
但禁止将其结果作为候选项、工具结果或记忆使用历史保存或展示。
仅保留安全的用量和阻断审计，并将整次运行标为 `BLOCKED`。

普通审查单元失败时继续处理其他单元。有成功单元时为 `PARTIAL_SUCCESS`，全部失败时为 `FAILED`。
后续运行按第 11 章规则只重新执行失败单元。

## 14. 度量与输出

M3 按审查单元及整次运行统计以下值。

| 指标 | 定义 |
|---|---|
| `tool_call_count` | 已预留的工具调用数，无论成功还是失败 |
| `tool_success_count` | 正文可以安全使用的调用数 |
| `tool_latency_ms` | 上下文工具处理时间总和，不计入 LLM 延迟 |
| `tool_reason_counts` | 按工具结果的安全原因代码统计的数量 |
| `dynamic_context_tokens` | 实际加入下一轮 LLM 输入的 Token 数 |
| `reflection_call_count` | 自我验证请求数，包括格式修复 |
| `reflection_supported_count` | `SUPPORTED` 数量 |
| `reflection_contradicted_count` | `CONTRADICTED` 数量 |
| `reflection_needs_context_count` | 自我验证为 `NEEDS_CONTEXT` 的数量 |
| `resumed_bundle_count` | 从检查点复用的审查单元数 |
| `reexecuted_bundle_count` | 恢复时重新执行的审查单元数 |

现有输入输出 Token、延迟、尝试次数与成本取评审轮次、格式修复、自我验证等全部 LLM 调用的合计。
工具处理时间单独度量，不计入 LLM 延迟。

保留现有 CLI 顶层字段及 `schema_version=1`。

现有 `metrics` 字段结构保持原样。
在 `run.versions` 中增加所用评审角色提示词和自我验证提示词的版本及内容哈希，功能未使用时取 null。
禁止返回工具正文、完整提示词、原始响应或检测到的字符串。

## 15. 提示词与本地数据集

增加以下受版本管理的资源。

| 资源 | 用途 |
|---|---|
| `prompts/review_agent_v1.yaml` | 返回工具请求或最终结果的审查代理循环 |
| `prompts/reflection_v1.yaml` | 对候选发现进行自我验证 |
| `application/review/agent_turn_schema.py` | 第 9 章的互斥轮次模式生成器，反映发现数上限 |
| `application/review/reflect_findings.py` | 第 10 章的自我验证模式生成器，固定候选数量 |

通用、安全和测试角色之间的差异作为共用资源内的固定区段管理，禁止从配置注入任意自由提示词。
将资源版本及内容哈希纳入 `RunVersions`、存储信息、运行同一性和评估条件。

封闭 JSON Schema 需要在运行时反映配置上限和目标候选数。
以上生成器是定义的唯一来源，禁止额外复制静态 JSON。修改生成器属于变更输出契约，须更新测试和评估。

`review_agent_v1@4` 的 `reviewer_profiles` 必须包含 `general`、`security`、`data` 和 `test` 四个键。
只将计划流程选定的 `reviewer_type` 对应内容展开到可信的「担当別の確認事項」区段。
拒绝未知键、缺失和空字符串。
自我验证提示词不生成新发现，只检查候选的主张、引用、目标行与执行路径是否一致，
并将其归入 `SUPPORTED`、`CONTRADICTED` 或 `NEEDS_CONTEXT` 这组封闭状态。

扩展 `DatasetLlmClient`，使其可离线复现 M3 各轮调用。
数据集包含用例 ID、审查单元 ID、调用类型、轮次编号、请求哈希和响应 JSON，
并检测重复键和未使用响应。
工具结果正文从测试仓库实际读取，禁止复制到数据集。

多轮格式使用 `schema_version=2`，各用例的 `responses` 记录
`review_unit_id`、`call_kind`、`turn_number`、`request_hash` 和 `result`。
以调用标识字段（不含请求哈希）和用例 ID 组成响应键。请求哈希为
`system_instruction + "\n" + user_content` 的 SHA-256，在返回响应前核对。
按 `<call_kind>:<review_unit_id>` 解释请求标签。同一审查单元和调用类型选择编号最小的未用轮次。
用例只要曾被选中，在客户端结束时仍有未用响应即失败。仅用例不匹配时允许默认响应。
用例匹配后，键或请求哈希不匹配时禁止回退到默认响应。
保留现有 `schema_version=1` 作为单响应兼容格式。

在 M2 的 B/C 对比中评估 M3 时，两组固定模型、温度、提示词、规则、工具、自我验证、并行数和数据集，
仅改变是否使用记忆。
