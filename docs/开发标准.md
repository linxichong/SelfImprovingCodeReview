# 自我改进型 AI 代码审查工具开发标准

## 1. 目的和适用范围

本文规定项目的软件开发流程、编码规范、命名规范、质量门禁、测试、安全及评审要求。

适用对象包括：

- Python 生产代码
- CLI、数据模型和数据库迁移
- 提示词、规则与记忆的 Schema
- 评估用例与评估脚本
- 测试代码
- CI/CD 配置与开发文档

采用以下规范用语：

- **必需**。必须遵守，违反时不得合并。
- **禁止**。不得实施，违反时按必需条款违规处理。
- **建议**。原则上应遵守，例外须在 PR 中说明理由。
- **可选**。可根据情况选用。

用于评审判定的规范条款原则上在开头标记 **必需**、**禁止**、**建议** 或 **可选**。
已有条款无显式标记时，将表达强制执行的「必须」「应当」和表达禁止的「禁止」「不得」视作强制条款，
将「原则上」「建议」「参考」视作建议，将「可以」「可选」视作可选。显式标记优先于其他措辞。
说明、背景和示例只提供参考。不同强度的要求应分别成条。

## 2. 工程原则

1. **优先保证正确性**。实现须准确且可验证。
2. **优先采取确定性处理**。能够以确定性逻辑准确完成的工作由代码执行。
3. **缩小变更范围**。一个 PR 只服务于一个明确目标。
4. **为边界定义类型**。对外部输入和模块边界设定类型和校验。
5. **按安全原则中断**。安全、敏感信息检查或策略发生违规时，默认中止处理。
6. **使行为可观测**。重要决策、费用、失败原因须可追踪。
7. **禁止隐式替代**。禁止吞掉异常或隐式回退。
8. **将测试纳入变更**。行为变更须新增或更新测试。
9. **评估须可复现**。固定模型、提示词、记忆与评估条件。
10. **实现须清晰易读**。避免过度抽象。

## 3. 技术基准

| 项目 | 标准 |
|---|---|
| Python | 3.14.x |
| 包与环境管理 | 统一使用 `uv` |
| 项目配置 | `pyproject.toml` |
| 格式化和静态检查 | Ruff |
| 类型检查 | mypy |
| 测试 | pytest + pytest-cov + diff-cover |
| 安全检查 | Bandit + pip-audit |
| 敏感信息检测 | detect-secrets 1.5.0 |
| Git 钩子 | pre-commit 4.6.2 |
| 数据库 | SQLite 和迁移 |
| 数据校验 | Pydantic |
| LLM 客户端库 | LiteLLM Python SDK |
| 文档 | Markdown |

**必需** 在 `pyproject.toml` 声明直接依赖与分组依赖，并以 `uv.lock` 作为包含传递依赖解析结果的唯一锁文件，两者均须提交。
使用 `uv add`、`uv remove` 和 `uv lock` 添加、删除和更新依赖，并分开管理生产和开发依赖。

**必需** 在 `pyproject.toml` 的 `[tool.uv].required-version` 中以 `==X.Y.Z` 精确固定 `uv` 版本，开发端和 CI 共用此版本。
CI 初始化引用该值，禁止重复声明其他版本。通过专用 PR 升级 `uv`，同步更新此值和 `uv.lock` 并通过全部质量门禁。

**必需** 初始化环境时运行 `uv lock --check` 和 `uv sync --frozen --all-groups`。
CI 禁止重新生成锁文件。统一使用 `uv run --frozen <command>` 执行命令，以免依赖开发机的全局包。

在 `pyproject.toml` 的直接依赖中管理 LiteLLM 的允许版本范围，禁止自动跨主版本升级。
实际版本由 `uv.lock` 固定。升级 LiteLLM 时须执行 AI 网关请求、异常转换、重试、结构化应答和用量获取的契约测试。

禁止使用 `venv + pip` 建立替代环境。禁止提交 `requirements.txt` 和 `requirements-*.txt` 作为依赖声明源或第二份锁文件。
外部工具确有需要时，使用 `uv export --frozen` 临时生成，生成物排除在版本管理之外。

## 4. 标准开发流程

```text
Issue 或需求
        ↓
范围与验收条件
        ↓
设计决策（记录在设计书或 Issue）
        ↓
创建分支
        ↓
复现失败 → 实现 → 回归验证证据
        ↓
本地质量检查
        ↓
Pull Request
        ↓
代码评审 + CI
        ↓
合并
        ↓
合并后验证
```

### 4.1 开发前准备

在 Issue 中记录以下内容：

- 待解决的问题或期望达到的目标
- 目标范围和明确的非目标事项
- 可验证的验收条件
- 对安全、隐私和兼容性的影响
- 对评估的影响

以下变更须先更新概要设计或详细设计的对应章节，或在 Issue 记录简明的设计决策：

- 增加核心模块或外部依赖
- 调整审查流程的执行顺序
- 修改审查发现、规则或记忆的 Schema
- 调整可向外部发送的数据范围
- 修改提示词或评估方法
- 增加代理、模型或检索方式

### 4.2 实现要求

- 调整行为时，按第 4.3 节先记录验收条件和失败复现。
- 每个提交须保持可理解和可构建。
- 功能 PR 中不得混入无关的大规模格式化或重构。
- 临时 TODO 应以 `TODO(#123): reason` 格式关联 Issue。
- 将重要决策的理由保存在代码注释、设计书或 Issue 中。

---

### 4.3 行为变更的验证顺序

- **必需** 按验收条件、复现变更前的失败、实现、变更后回归证据的顺序推进。
  验收条件须写明设计与契约依据、合法输入、拒绝条件和可观察的预期结果。
- **必需** 从契约、独立计算或固定资料确定预期。禁止根据实现输出反推预期，或仅为通过测试而改动预期。
  订正契约时须记录依据和条件变化。
- **必需** 复现和回归记录须标识代码、测试、输入和环境，包含命令、退出码和安全的观察结果。
  失败复现须显示被测行为违反了目标条件。工具未安装或 pytest 收集失败不能用作该证据。
- **必需** 无法复现或未执行时，记录理由和未确认范围。执行和通过状态须与实际一致。
  文档变更或保持行为的重构，使用基准结果和变更后的等效证据，禁止人为制造失败。
- **必需** 在 PR 的验证方法中记录条件及变更前后证据，或引用符合[验证记录模板](templates/行为变更_验证记录.md)的等效 Issue 记录。
  保留已有用例追踪和第 7.3 节要求的评审审批。
- **约束** 按顺序执行、预期值独立性及人工验收，都须有对应证据。审查人员核对条件的依据和失败原因。

### 4.4 AI 工作背景和交付格式

- **必需** 开始时明确目标、授权及非目标范围、设计章节、相关用例 ID、验收条件、检查命令和人工判断事项。
  可以引用现有 Issue 避免重复记录。
- **必需** 用例 ID 和审批须以事实为准，区分假设与未确认事项。只阅读相关设计章节。
- **必需** 完成时报告变更内容、行为的变化或维持情况、已执行的验证证据，以及待确认的条件。
  涵盖执行范围、退出状态及未执行理由。
- **必需** 将长期有效的决策用简体中文记录在相应设计章节或 Issue 中，并从报告引用。
  修改外部契约时同步更新设计，沿用现有评审审批要求。
- **参考** [工作委托与完成报告模板](templates/AI任务委托与完成报告.md)。
  PR 保留第 7.1 节的五项内容与第 7.2 节的条件项。

## 5. Git 分支规范

仓库使用 `main` 作为发布分支，`develop` 作为常规开发的集成分支。

### 5.1 分支职责

| 分支 | 职责 | 直接提交 | 接收的 PR |
|---|---|---|---|
| `main` | 保持已发布或可发布的稳定状态，是仓库默认分支 | 禁止 | 来自 `develop` 的发布 PR、来自 `hotfix/*` 的紧急修复 PR |
| `develop` | 面向下次发布的常规开发集成目标 | 禁止 | 来自 `feature/*`、`fix/*`、`refactor/*`、`docs/*`、`test/*`、`chore/*` 的 PR，及来自 `main` 的同步 PR |
| 主题分支 | 按 Issue 创建的短期工作分支 | 允许 | 原则上向 `develop` 提交 PR |

通过分支保护禁止向 `main` 和 `develop` 直接推送。变更必须通过 PR、必需 CI 检查和至少一位审查人员的审批。
开发人员通常以 `develop` 为检出和集成基准，托管平台上的默认分支是 `main`。

### 5.2 主题分支

从最新的 `develop` 创建主题分支。

```text
feature/<issue-id>-<description>
fix/<issue-id>-<description>
refactor/<issue-id>-<description>
docs/<issue-id>-<description>
test/<issue-id>-<description>
chore/<issue-id>-<description>
hotfix/<issue-id>-<description>
```

示例：

```text
feature/42-diff-line-mapper
fix/57-memory-scope-match
refactor/68-review-manager
```

- 使用小写字母、数字和连字符。
- **建议** 描述使用 2～5 个词。
- 每个分支只有一个主要目的。
- **建议** 分支存续时间控制在 5 个工作日内。
- 常规主题分支在创建 PR 前和合并前与最新的 `develop` 同步，在主题分支中解决冲突。
- 常规主题 PR 将 `develop` 作为基准，主题分支作为头分支。禁止用 `main` 作基准。
- 仅 `hotfix/*` 从 `main` 创建，并以 `main` 为基准。

### 5.3 发布：`develop` → `main`

1. 在 `develop` 确定发布范围，通过常规 PR 完成所需版本、变更日志、迁移和发布说明的更新。
2. 在 `develop` 通过必需 CI、全部测试、安全检查和所需评估，固定发布目标提交的 SHA。
3. 创建以 `develop` 为头分支、`main` 为基准的发布 PR，写明差异、已知风险、回滚步骤和发布版本。
4. 维护人员审批后，使用保留祖先关系的合并提交进入 `main`。发布 PR 禁止使用 squash merge 和 rebase merge。
5. 给 `main` 的合并提交添加 `v<major>.<minor>.<patch>` 格式的带注释标签，并从标签生成发布产物。
6. 发布过程中若产生 `main` 独有的提交，立即创建以 `main` 为头分支、`develop` 为基准的同步 PR，并以合并提交同步。

发布 PR 创建后需补充修复时，使用面向 `develop` 的主题分支和 PR 完成，再更新发布 PR。禁止直接修改 `main`。

### 5.4 紧急修复：`main` → `develop`

1. 从最新的 `main` 创建 `hotfix/<issue-id>-<description>`。
2. 通过必需 CI 和评审后，将面向 `main` 的 PR 以合并提交合入，并添加补丁版本标签。
3. 紧急修复发布后，创建以 `main` 为头分支、`develop` 为基准的同步 PR。
4. 在同步 PR 中解决与 `develop` 的冲突，通过必需 CI 后以合并提交同步。禁止在 `develop` 手工重复实现修复。

## 6. 提交规范

采用 Conventional Commits。

```text
<type>(<scope>): <summary>
```

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 保持外部行为的重构 |
| `test` | 新增或修正测试 |
| `docs` | 文档 |
| `perf` | 性能或 Token 费用改善 |
| `chore` | 依赖和工具维护 |
| `ci` | CI/CD |
| `security` | 安全加固 |

建议使用的范围：

```text
change / planning / review / context / rules / feedback
memory / llm / eval / cli / db / docs / design / infra
```

`docs` 用于一般文档，`design` 用于概要和详细设计书，`infra` 用于构建、部署与运行环境。
更新本标准或概要设计书时，可以使用 `docs(design)`。

示例：

```text
feat(change): add absolute diff line mapping
fix(memory): prevent cross-project scope matching
perf(context): stop retrieval at token budget
test(review): cover invalid evidence filtering
```

**必需** 摘要使用英文祈使语气，以小写字母开头，末尾不加句号。**建议** 不超过 72 字符。

## 7. PR 规范

### 7.1 所有 PR 的必填项

```text
摘要
动机
变更
验证方式
相关事项
```

以上五项为所有 PR 的**必需**内容。`验证方式` 简明记录已执行的验证方法和结果。
轻量维护未创建 Issue 时，可以在 `相关事项` 说明理由并引用提交或运维工单。

### 7.2 按变更内容填写的条件项

| PR 变更内容 | 追加项目 | 强度和条件 |
|---|---|---|
| 范围边界不明显，或拆分到后续 PR | `対象外` | **必需** |
| 修改生产代码、测试、配置、依赖或 CI | `品質確認結果` | **必需**，记录已执行的必需检查和结果 |
| 修改外部发送数据、认证与授权、敏感信息、依赖、安全要求或设置 | `Security / Privacy Impact` | **必需**，说明是否需要安全评审 |
| 修改模型、提示词、上下文、记忆、规则、分派、预算或工具调用 | `Token / Cost Impact` | **必需** |
| 修改模型、提示词、记忆、规则、审查流程或评估逻辑 | `Evaluation Impact` | **必需**，附变更前后结果 |
| 修改数据库 Schema、迁移、发布或紧急修复 | `Migration / Rollback` | **必需** |

条件不满足时省略整个标题和栏目，避免填写 `N/A` 占位。按实际变更内容判断适用性。
`docs/*` 或 `chore/*` 如涉及安全要求、配置或 LLM 行为变更，也须增加对应栏目。

未触发条件项的小型 `docs/*` 和 `chore/*` PR 只填写第 7.1 节的五项。
自动模板按变更路径或标签显示适用的条件项。

### 7.3 评审与合并规则

- **建议** 仓库差异保持在 400 行以内。PR 描述和自动生成的检查结果不计入。测试数据和生成物可例外，超过时在 PR 写明理由。
- **建议** 大型功能拆分为可以单独验证的纵向切片。
- **必需** 通过全部必需的 CI 检查。
- **必需** 获得至少一位审查人员的审批。
- **必需** 创建者处理所有标明必须处理的评审意见。
- **必需** 按第 7.2 节填写适用的条件项。
- **必需** 扩大或调整外部发送数据范围时须进行安全评审。
- **禁止** 审批自己创建的 PR。
- **建议** 面向 `develop` 的主题分支 PR 使用 squash merge。
- **必需** 从 `develop` 到 `main` 的发布 PR，从 `hotfix/*` 到 `main` 的紧急修复 PR，以及从 `main` 到 `develop` 的同步 PR 均使用合并提交。
- **必需** 最终提交消息遵守本规范。

## 8. 命名规范

### 8.1 包和目录结构

包名及标准目录结构以本节为准。发行包名为 `self-improving-code-review`，Python 顶层导入包名为
`self_improving_code_review`，采用 `src` 布局。禁止使用名为 `app` 的包或目录。

```text
.
├── pyproject.toml
├── src/
│   └── self_improving_code_review/
│       ├── __init__.py
│       ├── cli/
│       │   └── output.py
│       ├── application/
│       │   ├── review/
│       │   ├── feedback/
│       │   ├── memory/
│       │   └── evaluation/
│       ├── domain/
│       │   ├── change/
│       │   ├── finding/
│       │   ├── rule/
│       │   └── memory/
│       ├── infrastructure/
│       │   ├── git/
│       │   ├── llm/
│       │   ├── persistence/
│       │   └── context_tools/
│       └── security/
├── tests/
│   ├── unit/
│   ├── contract/
│   ├── integration/
│   ├── e2e/
│   └── evaluation/
├── config/
│   └── rules/
├── prompts/
├── migrations/
└── docs/
```

在 `pyproject.toml` 中配置控制台脚本 `review = "self_improving_code_review.cli.main:main"`，用户通过 `review ...` 启动 CLI。
禁止在仓库根目录添加独立的 `review.py` 或 `app/__init__.py` 作为入口。

概要设计的组件及对应位置：

| 组件 ID | 主要位置 | 职责 |
|---|---|---|
| CP-01 | `cli/`、`infrastructure/git/` | CLI、集成和 Git 适配器。面向用户的标准输出集中在 `cli/output.py` |
| CP-02、CP-04 | `domain/change/` | 变更解析、文件筛选 |
| CP-03 | `security/` | 敏感信息检查策略或服务 |
| CP-05～CP-10、CP-14、CP-15 | `application/review/` | 评审用例，协调及执行 LLM 自检 |
| CP-11 | `infrastructure/context_tools/` | 文件、符号、代码检索适配器 |
| CP-12、CP-13 | `domain/finding/` | 位置和证据的验证策略及结果 |
| CP-16 | `application/feedback/` | 反馈用例 |
| CP-17、CP-18 | `application/memory/`、`domain/memory/` | 记忆分析与治理 |
| CP-19 | `application/evaluation/` | 评估用例 |
| CP-20 | `infrastructure/llm/` | 使用 LiteLLM 的 AI 网关适配器 |
| 数据持久化实现 | `infrastructure/persistence/` | SQLite 仓储、迁移适配器 |

- **必需** 生产代码位于 `src/self_improving_code_review/` 下，导入从 `self_improving_code_review...` 开始。
- **必需** `application` 协调用例。`domain` 禁止依赖 CLI、数据库或包括 LiteLLM 在内的 LLM SDK。
- **必需** `infrastructure` 实现领域层或应用层定义的接口，依赖方向须保持一致。
- **必需** LiteLLM 只能在 `infrastructure/llm/` 内导入。禁止向其他层暴露 LiteLLM 特有的请求、应答和异常类型。
- **必需** 测试位于 `tests/<test-level>/` 下，与生产模块结构对应。
- **可选** 能放在单一文件的小组件可以实现为对应包内的模块，避免按组件机械增加包。

### 8.2 标识符命名

遵循 PEP 8，并采用以下项目规范：

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块和文件 | `snake_case` | `diff_parser.py` |
| 包及目录 | `snake_case` 格式的名词 | `review`、`memory` |
| 函数及方法 | 以动词开头的 `snake_case` | `parse_diff()` |
| 变量 | `snake_case` | `memory_token_budget` |
| 类 | 以名词命名的 `PascalCase` | `ReviewPlanner` |
| 异常 | `PascalCase` + `Error` | `InvalidDiffError` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_TOOL_CALLS` |
| 非公开成员 | `_` 前缀 | `_validate_line()` |
| 类型别名 | `PascalCase` | `FindingId` |
| 枚举类 | `PascalCase` | `FindingStatus` |
| 枚举值 | `UPPER_SNAKE_CASE` | `NEEDS_CONTEXT` |
| 测试文件 | `test_<subject>.py` | `test_diff_parser.py` |
| 测试函数 | `test_<behavior>_<condition>` | `test_parse_diff_rejects_binary_file` |

- 使用完整、具体的英文单词。
- 只使用 `id`、`api`、`cli`、`llm`、`pr`、`sql`、`json` 等通用缩写。
- 布尔值以 `is_`、`has_`、`can_` 或 `should_` 开头。
- 集合使用复数。
- 名称包含单位，例如 `timeout_seconds`、`latency_ms`、`token_count`。
- 输入输出类型名称加 `Request`、`Response`、`Input`、`Result` 等后缀。
- 禁止使用 `process_data()`、`handle_stuff()`、`tmp` 等含义模糊的名称。

推荐示例：

```python
changed_files = diff_parser.parse(diff_text)
validated_findings = validate_findings(candidate_findings)
review_manager = ReviewManager(...)
```

## 9. Python 编码规范

### 9.1 格式化和导入

- 统一使用 Ruff 格式化，行长上限为 100 字符。
- 字符串原则上使用双引号。
- 使用 Ruff 排列导入。
- 文件末尾只保留一个换行。
- 禁止通配符导入。
- 通过调整模块边界解决循环依赖，禁止用函数内导入掩盖它。

### 9.2 类型

- 为生产代码中的公开函数、方法和类属性添加类型注解。
- 使用 `list[str]`、`str | None` 等 Python 3.14 类型语法。
- 必须校验外部输入、LLM 输出、配置和数据库边界。
- 禁止无理由使用 `Any`。
- 使用 `# type: ignore` 时记录错误代码和理由。
- 禁止使用 `cast()` 掩盖尚未验证的运行时输入。

```python
def select_applicable_rules(
    changed_file: ChangedFile,
    rules: Sequence[ReviewRule],
) -> list[ReviewRule]: ...
```

### 9.3 函数和类

- 函数只承担一个主要职责。
- 差异解析、匹配、预算计算和验证优先使用纯函数。
- **建议** 函数控制在 40 行内，模块控制在 400 行内。长度作为评审职责与可读性的指标。
  Ruff `PLR0915` 等检查不将此设为自动合并门禁。超过时在 PR 中说明当前职责划分合理的原因。
- **建议** 参数超过 5 个时，考虑用配置对象或数据模型归集。
- 禁止布尔位置参数，使用关键字参数或枚举。
- 只在需要状态、生命周期或可替换策略时使用类。
- 避免为只有一个实现且无替换计划的对象引入抽象基类。

### 9.4 状态与数据

- 领域输入与结果优先使用不可变模型。
- 禁止直接修改调用者传入的集合。
- 让名称或接口清楚体现副作用。
- **必需** 使用带时区的 UTC 时间，由 Ruff 的 `DTZ` 规则自动检查。
- 使用 `Decimal` 精确计算费用。
- 禁止模块级可变全局状态。

### 9.5 文档字符串和注释

- **必需** 生产代码中的公开 API 与一般模块使用 Google 风格文档字符串。
  公开 API 包括名称不以 `_` 开头的类、函数和方法，以及通过 `__all__` 公开的对象。
- 新类、方法、函数均使用日文文档字符串说明调用目的与职责，包括非公开项。省略显而易见的逐行注释。
- **必需** 文档字符串说明适用的契约、参数、返回值、异常和重要约束，禁止简单复述类型注解和代码。
- 使用 Ruff 的 `D` 规则和 `pydocstyle.convention = "google"` 自动检查。对 `tests/**` 排除 `D`，对 `__init__.py` 仅排除 `D104`。
- **建议** 即使是非公开算法，也使用文档字符串说明复杂算法的意图、前提和不变条件，必要性由评审判断。
  **可选** 明确易懂的非公开辅助逻辑可以省略文档字符串。
- **必需** 使用 `# noqa: D...` 时，在同一行或上一行的注释说明理由，并获得审查人员批准。

注释解释实现的必要性。

```python
def map_new_file_lines(diff_hunk: str) -> LineMap:
    """差分行を変更後ファイルの絶対行番号へ対応付ける。

    削除行は変更後ファイルに存在せず、コメントを紐付けられないため、
    対象から除外する。

    Raises:
        InvalidDiffError: 差分ブロックのヘッダーを解析できない場合。
    """
```

## 11. 异常处理

推荐的异常层级：

```text
DomainError
├── InvalidDiffError
├── InvalidFindingError
├── TokenBudgetExceededError
├── MemoryConflictError
└── PolicyViolationError

InfrastructureError
├── LlmClientError
├── GitCommandError
├── DatabaseError
└── ToolExecutionError
```

- 仅捕获能够正确处理的异常。
- 禁止空 `except`，也禁止捕获 `Exception` 后继续处理。
- 进程边界可以捕获未知异常，必须记录并返回稳定的退出码。
- 通过 `raise ... from exc` 保留原异常链。
- 错误包含操作、目标和原因。禁止包含敏感信息。
- 只对暂时性故障重试，须设置次数上限及递增等待时间。
- Schema、策略和安全失败须显式处理，禁止自动修复或隐式忽略。

## 13. LLM、提示词、规则和记忆

### 13.1 LLM 调用

- 所有调用均通过共用的 `LlmClient`。
- 必须设置超时、重试和 Token 上限。
- 正式评估固定具体模型版本，禁止使用 `latest`。
- 记录 Token、延迟和费用。
- 输出必须经过 Schema 验证。
- 提供方特有的类型限于适配器边界。
- 本地开发和自动化测试默认使用固定数据集适配器，禁止隐式调用外部 LLM。
- 只有显式使用专用配置、授权外部发送并在环境变量中提供凭据时，才可使用真实 AI 网关。
- 分开管理开发集和测试集。禁止将测试数据复用于记忆生成或正式评估。

### 13.2 提示词

- 将提示词作为有版本的资源管理。禁止在业务代码中拼接长提示词。
- 修改提示词时更新 `prompt_version`。
- 明确分隔指令和不可信数据。
- 将差异、源输入、PR 描述、反馈中的命令性语句一律当作数据处理。
- 提示词变更须附固定用例的前后评估结果。
- 文件选择、行号计算和适用范围匹配由确定性代码执行。

### 13.3 规则

- 禁止复用已发布的规则 ID 或改变其含义。
- 规则必填项为 `id`、`category`、`severity`、`scope`、`instruction`。
  `severity` 取 `critical`、`high`、`medium` 或 `low`。
- `scope` 是包含 `languages`、`paths`、`keywords` 数组的结构化对象，至少一个数组有值。
  尽可能明确适用范围。禁止将高噪声规则应用到整个仓库。
- 按概要设计第 9.1 节相同的 Schema 验证规则 YAML。CI 须拒绝缺少必填项、未知 `severity` 和非法范围。
- 修改规则时补充正常和异常用例。

```text
<LANGUAGE_OR_DOMAIN>.<ISSUE_TYPE>
JAVA.NULL_DEREFERENCE
SECURITY.SQL_INJECTION
TEST.MISSING_FAILURE_PATH
```

### 13.4 记忆

- 只有 `active` 记忆可进入评审上下文。
- 记忆有项目、适用范围、极性、证据和状态。
- 禁止将原始反馈直接拼接到提示词。
- `suppress` 表示需要更强证据，符合条件的发现仍可报告。
- 禁止仅凭记忆压制重大安全发现。
- 保留记忆的变更历史和依据链。

## 14. 数据库与 Schema

- 所有表均使用稳定的主键和明确的外键。
- 时间以 UTC 保存。
- 枚举在应用程序和数据库约束两处验证。
- 为常用检索字段添加索引，增加索引时说明写入成本。
- 禁止改写已共享的迁移。

- 将数据访问集中在仓储或存储适配器，禁止将 SQL 散布在业务逻辑中。

## 15. 测试规范

### 15.1 测试级别

| 类型 | 对象 | 外部服务 |
|---|---|---|
| 单元 | 解析、匹配、预算和验证 | 不使用 |
| 契约 | LLM Schema、Git 适配器及存储 | 原则上不使用 |
| 集成 | 处理流程、SQLite、工具调用 | 可控桩 |
| 评估 | 评审质量和费用 | 固定模型 |
| 端到端 | 从 CLI 到最终输出 | CI 使用模拟 LLM |

### 15.2 测试要求

- 使用准备、执行、验证三阶段。
- 每个测试验证一个主要行为。
- 测试名体现条件和预期结果。
- 禁止依赖网络、当前时间或随机顺序。
- 时间、UUID、随机数和 LLM 应答均可注入。
- 禁止使用真实敏感信息。
- 缺陷修复须添加在修复前失败的回归测试。
- 解析、适用范围匹配、行映射、预算和验证须有参数化边界测试。
- 语义验证条件须有直接证据。提示词快照只能提供补充证据。

### 15.2.1 设计用例追踪

- **必需** 为相关测试函数添加稳定 ID，例如 `@pytest.mark.case("UT-M1-004")`。
  允许多个 ID 和多个函数相互关联。关联须精确到函数。
- **必需** 执行 `uv run --frozen python scripts/check_case_traceability.py`，
  验证全部设计 ID 均已关联、没有未定义 ID、对应表是最新版本。禁止豁免缺失关联。
- **必需** 关联变化时使用 `--write` 重新生成[对应表](测试用例对应表.md)。常规 pytest 也验证对应表。
- **必需** ID 关联与验收完成分别记录。使用不同测试层或只验证部分条件的证据，应在[对应补充](测试用例对应补充说明.md)记录待确认条件。
- **必需** 为缺陷复现测试和缺陷工单关联已有或新增的设计 ID。
- **必需** 通过 `uv run --frozen pytest --junitxml=.review/test-results.xml` 输出证据 XML。
  用各测试的 `properties/case_ids` 和节点 ID 按设计 ID 追踪结果。参数化条件由节点 ID 后缀识别。
- **可选** 可以通过 `uv run --frozen pytest -k UT-M1-004` 选择特定用例。

### 15.2.2 外部行为和不变条件

- **必需** 主判据是返回值、CLI 输出、保存状态、拒绝结果及失败时的副作用。
  禁止仅按内部调用次数或私有结构判定验收。允许验证发送范围或重试上限等契约规定的调用约束，也允许直接验证确定性的单元逻辑。
- **必需** 修改解析、认证或授权、事务、恢复时，列出正常条件、拒绝边界、失败路径及须保持的不变条件。
  例如，拒绝范围外输入、拒绝访问其他归属、回滚后无部分保存，以及固定输入变化时禁止复用旧结果。
- **可选** 属性测试可以使用多个输入验证设计不变条件，须保留可复现的种子和生成条件。
  变异测试可以在临时副本上模拟边界或校验缺失，验证目标测试能否检出缺陷。
  存活变异分为等价、非目标和测试不足，不设统一成功率。
- **禁止** 用同一生产函数生成预期值、仅以覆盖率作验收依据、捏造过去未运行的证据。
  通过 uv 添加依赖。常规测试禁止调用真实 LLM。

### 15.3 覆盖率

- **必需** 总体行覆盖率至少为 85%。
- **必需** 差异行覆盖率至少为 90%。仅当差异中生产 Python 的可执行行数为 0 时标记为 `N/A`，并在 CI 报告写明分母为 0。
- 重点验证差异解析、行映射、适用范围匹配、Token 预算、验证和安全判定逻辑的各个分支。
- 禁止添加只为了提高覆盖率数值的无效测试。

| 指标 | 分母 | 排除项 |
|---|---|---|
| 总体行覆盖率 | coverage.py 识别的 `src/self_improving_code_review/**/*.py` 的全部可执行行 | 下列共同排除项 |
| 差异行覆盖率 | 相对于 PR 比较基准 SHA 新增或修改的上述生产 Python 可执行行。新增文件包含全部可执行行 | 下列共同排除项 |

共同排除项包括：

- `tests/`、`config/`、`prompts/`、`migrations/` 和 `docs/`，均位于生产包之外。
- 注释、空行、纯类型声明等 coverage.py 判定为不可执行的行。
- 由工具生成且禁止手工编辑的代码。须在 `pyproject.toml` 写明路径、生成流程和重新生成步骤，并获得维护人员审批。

`cli/`、`application/`、`domain/`、`infrastructure/`、`security/` 均作为生产代码计入分母。
由 Python 实现的提示词读取和 CLI 参数定义也须计入。
仅可用 `# pragma: no cover`、`omit`、`exclude_lines` 排除不可执行的平台分支等特定情况。
须在行内说明原因，在 PR 说明安全或质量影响，并获得审查人员批准。禁止仅为达到覆盖率目标排除代码。

差异采用 PR 的实际比较基准 SHA。常规主题 PR 及从 `main` 到 `develop` 的同步 PR 使用 `develop` 的合并基点。
发布 PR 及紧急修复 PR 使用 `main` 的合并基点。
固定 CI 检出的 PR 比较基准 SHA。计算不随分支最新头提交移动。

### 15.4 LLM 评估

- **必需** 在报告中明确评估用途为开发调优、已知缺陷回归或冻结的独立验收，并另行记录候选、技术检查、人工验证、审批和发布状态。
- **必需** 提示词和规则变更使用相同固定条件比较前后情况，按组和轮次报告漏报、误报、严重问题 ID 的保留和缺失，以及 Token、延迟和费用。

  分别记录 AI 技术检查及实际负责人完成的验证、裁定、审批和验收。
- **参考** [独立性管理](评估数据_独立性管理.md)及[比较记录模板](templates/评估变更_比较记录.md)。

禁止使用测试数据集的反馈生成记忆。

全局排除须注明理由，尽可能使用范围较小的按文件排除。

Ruff 用于格式、导入和常见代码质量问题检查，配置不启用安全检查 `S` 系列。
Bandit 是 Python 代码安全静态分析的唯一判定工具。`security-scan` 任务运行 `bandit -q -r src/self_improving_code_review`。
禁止在 Ruff 和 Bandit 中重复管理同一安全规则。

`T20`（`flake8-print`）与第 12 章 CLI 输出例外采用以下规则。
面向用户的标准输出和标准错误集中在 `cli/output.py` 的写入函数，直接调用 `print()` 仅限该模块。
`per-file-ignores` 的 `T201` 豁免仅用于 `src/self_improving_code_review/cli/output.py`。
包括 `cli/` 下其他模块在内，所有其他模块均禁止使用 `print()`，禁止通过 `# noqa: T201` 扩大豁免范围。

### 16.3 mypy 配置

```toml
[tool.mypy]
python_version = "3.14"
files = ["src/self_improving_code_review"]
exclude = "^tests/"
strict = true
warn_unreachable = true
show_error_codes = true
pretty = true
```

- **必需** 对整个 `src/self_improving_code_review` 执行 mypy `strict`，并将 `mypy src/self_improving_code_review` 成功作为合并门禁。
- **必需** `tests` 排除在必需 mypy 检查范围之外，以 Ruff 和 pytest 作为合并门禁。测试数据、模拟对象及猴子补丁等无需采用生产代码的 `strict`。
- **建议** 为测试辅助逻辑的公开接口和依赖类型的测试添加类型注解。类型检查有益的测试模块可以单独加入 mypy 范围，并在 PR 说明原因。
- **必需** 测试排除在必需范围之外时，仍禁止通过 `Any`、`cast()` 或无类型测试替身掩盖生产包类型错误。

现有生产包无法一次满足 `strict` 时，按模块逐步收紧，并用 Issue 管理剩余工作。新模块遵守完整标准。

### 16.4 提交前处理

敏感信息检测引擎固定为 `detect-secrets 1.5.0`。
pre-commit 和产品功能 FN-03 共用引擎版本及检测插件集合，分别采用以下适配器和抑制策略。

| 用途 | 适配器 | 对象 | 抑制策略 | 检出后处理 |
|---|---|---|---|---|
| 仓库门禁 | `detect-secrets` pre-commit 钩子 | 暂存文件 | 经安全评审的 `.secrets.baseline` 及仓库管理的显式允许列表 | 提交或 CI 失败 |
| 产品 FN-03 | `SecretScanner` 调用 detect-secrets Python API | 差异和各上下文获取工具输出的全部行 | 禁用基准已有结果、输入中的允许列表注释和按路径抑制 | 向 LLM 发送前阻断整个评审 |

`.secrets.baseline` 保存仓库门禁已知误报的指纹及插件与阈值设置。禁止将真实敏感信息登记到基准中。
新增或更新基准时，在 PR 说明安全影响、检测类型及误报依据，获得安全审查人员的批准。

FN-03 读取相同的插件和阈值配置。禁止使用 `.secrets.baseline` 的结果作为发送允许列表。
检查在进程内存中执行，禁止把候选字符串写到临时文件、标准输出或日志。
禁用敏感信息的外部验证功能，禁止向第三方服务发送候选值。

依赖锁和 pre-commit 的 `rev` 固定为同一 detect-secrets 版本。
CI 检查版本、插件和阈值一致性，并运行以合成敏感信息语料分别输入两种适配器的契约测试。
契约测试位于 `tests/contract`，在第 16.5 节的 `contract-test` 任务执行。
产品 FN-03 的结果必须至少与仓库门禁同等严格。若有测试数据只被仓库门禁检出，CI 失败。

`.pre-commit-config.yaml` 标准配置：

```yaml
minimum_pre_commit_version: "4.6.2"

repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-toml
      - id: check-json

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.16.7
    hooks:
      - id: ruff-format
      - id: ruff-check

  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.5.0
    hooks:
      - id: detect-secrets
        args:
          - --baseline
          - .secrets.baseline
        exclude: ^\.secrets\.baseline$
```

最低检查项：

- 行尾空白
- 文件末尾修正
- YAML、TOML、JSON 语法检验
- Ruff 格式
- Ruff 静态检查
- 敏感信息检测

```bash
uv run --frozen pre-commit install
uv run --frozen pre-commit run --all-files
```

### 16.5 CI 任务

```text
dependency-sync
lint
type-check
unit-test
contract-test
integration-test
e2e-test
coverage
security-scan
evaluation-smoke
```

任务与测试目录按下表对应，并与第 15.1 节的测试类型一一对应。

| 任务 | 执行对象 | PR 必需 |
|---|---|---|
| `unit-test` | `tests/unit` | 必需 |
| `contract-test` | `tests/contract` | 必需 |
| `integration-test` | `tests/integration` | 必需 |
| `e2e-test` | `tests/e2e`（模拟 LLM） | 必需 |
| `evaluation-smoke` | `tests/evaluation` 中带 `smoke` 标记的最小用例（模拟或已记录的 LLM 应答） | 必需 |
| 定期工作流 | `tests/evaluation` 中的全部用例（固定模型、真实 LLM） | 可在 PR 之外执行 |

`tests/evaluation` 是统一的评估测试目录，以 `smoke` 标记区分 PR 必需 CI 和定期执行。
带 `smoke` 标记的用例只使用模拟或已记录的 LLM 应答。第 15.1 节的固定模型用于定期工作流的正式评估。

`dependency-sync` 以 `[tool.uv].required-version` 的精确版本初始化 `uv`，执行 `uv lock --check` 和 `uv sync --frozen --all-groups`。
版本不符、锁缺失、锁不一致或检测到变更时失败。后续任务使用该同步环境，通过 `uv run --frozen` 执行命令。

`lint` 执行 `uv run --frozen ruff format --check .` 和 `uv run --frozen ruff check .`。
`type-check` 执行 `uv run --frozen mypy src/self_improving_code_review`。
`coverage` 检查总体 85% 和差异 90% 两项门禁。
`security-scan` 执行 Bandit、依赖审核及 detect-secrets 仓库门禁。
禁止把 `tests` 纳入 `type-check`，或在 `lint` 重新启用 Ruff `S`，以维持上述职责安排。

第 16.4 节要求的两种敏感信息检测适配器契约测试放在 `tests/contract`，由 `contract-test` 执行。
完成条件中的 FN-03 契约测试通过由 `contract-test` 的成功确认。
`security-scan` 限于 Bandit、依赖审核和仓库门禁，禁止重复执行契约测试。

`evaluation-smoke` 使用固定的模拟或已记录的 LLM 应答验证处理流程和 Schema。
真实模型的完整评估定期或手动执行。

## 18. 禁止事项

违反以下任何一项均禁止合并。

- **禁止** 直接向 `main` 或 `develop` 提交或推送。
- **禁止** 从常规主题分支直接向 `main` 创建 PR。
- **禁止** 发布或紧急修复后将 `main` 独有的变更留在 `main`，不向 `develop` 同步。
- **禁止** 为通过 CI 停用静态检查、类型检查或测试。
- **禁止** 无理由增加范围宽泛的 `noqa`、`type: ignore` 或安全检查排除。
- **禁止** 捕获异常后不记录、不返回也不处理地继续执行。
- **禁止** 在日志、测试数据、提示词或原始输入中包含真实敏感信息。
- **禁止** 使用未经 Schema 校验的 LLM 输出。
- **禁止** 将行号、路径和适用范围等可确定性处理的判断交给 LLM。
- **禁止** 改动提示词却不更新版本。
- **禁止** 从测试数据集的反馈生成记忆。
- **禁止** 正式评估使用模型别名 `latest`。
- **禁止** 仅凭 LLM 自报的 `confidence` 排除发现。
- **禁止** 仅凭 `suppress` 记忆隐藏重大安全发现。
- **禁止** 在功能 PR 中混入无关重构或批量格式化。
- **禁止** 未说明用途、安全影响和备选方案就添加依赖。

## 19. 例外和规范变更

偏离本规范时，在 PR 中记录：

```text
申请豁免的规则
Reason
Scope
Risk
Mitigation
失效日期或后续 Issue
Approver
```

在 `Approver` 填写明确批准该申请的维护人员标识。申请者禁止担任 `Approver`，获得审批后才可应用例外。

永久例外须纳入本标准或相应概要与详细设计文档。

变更本标准也须经过 PR 评审。放宽质量门禁须获得维护人员的明确批准并提供恢复计划。

质量检查共用入口为 `scripts/check_quality.py`。执行方式和 CI 配置参见[质量门禁执行手册](质量门禁执行手册.md)。
