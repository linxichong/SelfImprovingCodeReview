# M2 详细设计书：反馈与记忆循环

## 1. 目的与范围

M2 保存对 M1 审查发现的评价和漏检报告。由 LLM 提炼记忆候选，经过人工批准后注入后续审查。使用固定测试数据集比较 B/C 组。范围为 FN-07、FN-14～18。高级冲突处理、失效和向量检索归入 M5。

## 3. 反馈契约

~~~python
class FindingFeedbackInput:
    run_id: RunId
    finding_id: FindingId
    label: FeedbackLabel
    reason: str
    actor_id: str


class MissedIssueInput:
    run_id: RunId
    file: NormalizedPath
    start_line: int | None
    symbol: str | None
    issue_type: str
    severity: Severity
    description: str
    evidence: str
    actor_id: str
~~~

对已有审查发现的评价不得使用 `MISSED_ISSUE`。漏检报告至少提供 `start_line` 和 `symbol` 之一，内部标签固定为 `MISSED_ISSUE`。验证其运行归属及目标修订上的文件与位置。

幂等键如下。

- 审查发现评价：`run_id:finding_id:actor_id:label:reason_hash`
- 漏检问题：`run_id:file:location:issue_type:evidence_hash`

检查自由文本的长度、控制字符与提示词边界。仅追加记录，订正通过带 `supersedes_feedback_id` 的新记录完成。

### 3.1 保存反馈与提取候选的执行边界

保存反馈与通过 LLM 提取记忆候选使用不同事务。按以下顺序执行。

1. 验证输入、运行与审查发现的归属关系，以及目标修订上的位置。
2. 在短数据库事务中追加并提交反馈。
3. 在另一短数据库事务中向 `memory_extraction_runs` 写入 `PENDING` 状态的提取意图。
4. 在事务外获取最少必需上下文，检查敏感信息，调用 LLM 并验证响应。
5. 成功时，在同一事务中保存新记忆 ID、不可变版本 1、依据关联和 LLM 用量，并将提取运行设为 `SUCCESS`。
6. 失败或拦截时保留反馈，保存安全错误码和已取得的用量，将提取运行设为 `FAILED` 或 `BLOCKED`。

提取幂等键为 `memory-extraction:project_id:source_revision:ordered_feedback_ids:feedback_content_hashes:context_locator_hash:prompt_hash:model` 的 SHA-256。同键已完成时返回既有候选，`PENDING/RUNNING` 视为冲突并禁止重复执行。重试 `FAILED` 时递增相同 `extraction_id` 的 `attempt`，禁止创建新候选。只有输入、提示词或模型变化才创建新的提取运行。

CLI 结果分别返回 `feedback_id`、`feedback_status=RECORDED`、`extraction_id` 和 `candidate_status`。候选提取失败时，仍须显示反馈已保存。LLM 失败、格式不合法、检出敏感信息分别返回退出码 2、3、4，重新执行同一命令时按上述幂等契约恢复。

提取运行具有 `PENDING/RUNNING/SUCCESS/FAILED/BLOCKED` 状态。每次状态变更记录 UTC 时间，通过比较并交换（CAS）获取 `RUNNING`。禁止多个进程并发执行同一提取运行。

调用外部 LLM 期间不持有数据库事务。提取结果或用量保存失败时，不得返回成功，且应保持同一提取运行可恢复。

## 4. 记忆候选

~~~json
{
  "category": "framework",
  "scope": {
    "languages": ["java"],
    "frameworks": ["spring"],
    "paths": ["src/**/controller/**"],
    "symbols": [],
    "keywords": ["@Valid"],
    "risk_tags": ["validation"]
  },
  "fact": "フレームワークは、注釈付き引数を処理開始前に検証する。",
  "review_instruction": "検証不足を報告する前に、回避経路の実証を要求する。",
  "polarity": "suppress",
  "confidence": 0.82,
  "evidence_summary": "フィードバックと対象リビジョンで確認済み。"
}
~~~

生成提示词仅接收已验证的审查发现、反馈和最少必需的周边信息，均视为不可信数据。检查模式、字符串长度、枚举类型、适用范围模式及指令注入模式，始终以 `PENDING` 保存。

### 4.1 生成候选时的安全边界

生成候选的全部 LLM 调用通过 `LlmClient`，遵循以下固定顺序。

```text
经验证的反馈／审查发现
→ 获取最少必需上下文
→ 路径策略
→ Token 预算
→ 敏感信息检查，并封存 ScannedPayload
→ 提示词边界
→ LlmClient
→ 提取单个 JSON
→ 按禁止额外属性的模式验证
→ 验证记忆策略
```

将反馈、审查发现依据、从目标修订取得的代码片段及自由文本视为不可信输入。按发送单元在发送前执行基于内容的敏感信息检查，内容变化后重新检查。不能以路径名排除或提示词注入模式检查替代敏感信息检查。

发现任一疑似敏感信息时不得发送到 LLM，将该提取运行设为 `BLOCKED`。保留已保存的反馈，禁止保存记忆候选、完整上下文、完整提示词及检出字符串。只可记录输入源类型、工具名、规范化文件、行、检测器名称、引擎版本及负载哈希。补充上下文后，须对包含新增内容的最终发送负载重新封存。

提取提示词在 `prompts/` 中进行版本管理。`memory_extraction_runs` 保存提示词版本与哈希、模型、尝试次数、输入和输出 Token、总等待时间及可取得的费用。响应格式无效时只修复一次。认证和请求错误不重试，仅对临时通信故障由适配器进行有上限的重试。

将 `suppress` 规范化为要求有力依据的指令，禁止用作删除命令。拒绝压制重大安全问题的候选。原始反馈不得直接进入检索。

## 5. 状态转换

| 原状态 | 操作 | 新状态 | 条件 |
|---|---|---|---|
| ― | 提取 | `PENDING` | 存在反馈且通过模式验证 |
| `PENDING` | 批准 | `ACTIVE` | 具备维护权限并确认适用范围 |
| `PENDING` | 驳回 | `REJECTED` | 具备维护权限并提供理由 |
| `PENDING` | 检出冲突 | `CONFLICT` | 可能与有效记忆矛盾 |
| `CONFLICT` | 缩小适用范围并批准 | `ACTIVE` | 人工调整适用范围 |
| `ACTIVE` | 替换或停用 | `SUPERSEDED/ARCHIVED` | M5 正式提供 |

所有转换均记录操作者、UTC 时间、理由及前后版本。TBD-06 解决前，仅使用本地开发环境中显式配置的维护人员名单，禁止启用生产审批。

`memory_id` 标识逻辑记忆，内容由 `(memory_id, version)` 固定且不可变。提取时创建版本 1，仅批准或驳回不增加内容版本。更改适用范围、事实、审查指令、极性、置信度或依据摘要时，先创建新版本再进行状态转换，禁止覆盖当前版本。

`memories.current_status` 表示状态，`memories.current_version` 指向当前内容，所有变更记录在 `memory_transitions`。快照固定引用创建时的 `(memory_id, version, content_hash)`，因此后续编辑及状态变更不会影响该快照。

更新必须通过 `memories.lock_version` 使用乐观锁。同一版本上的重复批准或适用范围更新只允许一方成功。记忆内部版本号从 1 开始单调递增，允许跳号，禁止复用。

## 6. 最小冲突判定

从同一项目的有效记忆中提取适用范围相交、类别相同且事实或指令的规范化哈希不同的记忆作为冲突候选。以 `CONFLICT` 呈现待确认的语义冲突，禁止自动判定语义矛盾或自动更改现有有效记忆。

## 7. 检索

仅检索项目 ID 匹配、`memories.current_status=ACTIVE` 且由 `memories.current_version` 指向的不可变版本。

适用范围中有值的组之间取逻辑与，同组候选之间取逻辑或。
只有同一文件满足指定的路径、语言、框架、符号和关键词条件时，才给该匹配计分。
风险标签与审查单元的分类比对。任一指定条件不匹配时计 0 分，禁止将不同文件的匹配合并后注入。
多个文件匹配时取最高分，文件数量不扩大优先级。

| 匹配项 | 分数 |
|---|---:|
| 完全匹配的路径 | +100 |
| 符号 | +80 |
| 框架 | +60 |
| 语言 | +40 |
| 风险或分类 | +30 |
| 关键词 | +10 |

同分时按 `confidence desc, confirmed_at desc, memory_id asc` 排序。最多选取前 K=5 条，总上限为 1,200 Token，每条上限为 200 Token。超限记忆整条排除，增加 `memory_truncated_count`。

快照将运行中固定可用的有效记忆 `memory_id/version/content_hash` 按 ID 排序后计算哈希。审查发现只关联实际放入提示词的记忆。

实现中，快照固定构建上下文时实际加入提示词的记忆。审查期间有效记忆发生变化时也不重新读取，保存该次运行所用的内容。已经构建记忆上下文的运行，即使审查发现数或检索数为 0，也保存快照，包括空集合。

`memory` 模式的审查幂等键包含运行开始时全部有效记忆的集合哈希，由按 ID 排序的记忆 ID、版本与内容哈希计算。增加、更新或停用有效记忆后，即使差异及配置相同，也开启新的审查运行。`baseline` 和 `rules` 模式的幂等性不受记忆状态影响。

## 8. 应用于审查

B 组只使用规则，C 组使用相同的规则快照和固定记忆快照。将记忆置于可信规则与不可信差异之间的准可信区。

沿用 M1 验证。记忆不得直接覆盖行、依据或严重程度。重大审查发现即使匹配 `suppress` 记忆，仍按常规流程验证。

## 9. 持久化模式

| 表 | 主要列及约束 |

| `memory_snapshots` | snapshot_id PK、project_id、snapshot_hash、created_at |

| `ground_truth_sets` | set_id PK、split、version、set_hash、status、approved_by、published_at |
| `ground_truth_cases` | set_id、序号、变更引用、创建者、验证者、批准者、status。也保存 0 问题的变更 |
| `ground_truth_issues` | issue_id、set_id、拉取请求或提交、位置、分类、严重程度、依据、输入源、各操作者、status |

`memories.current_version` 与 `memories.current_status` 使用 NOT NULL，并通过枚举 CHECK 约束验证状态值。从 `memories(memory_id,current_version)` 到 `memory_versions(memory_id,version)` 的循环引用采用 `DEFERRABLE INITIALLY DEFERRED`，在同一事务中创建逻辑 ID 和版本 1。`memory_extraction_runs.candidate_memory_id/version` 仅在成功前允许 NULL。状态为 `SUCCESS` 时必须有值并满足指向记忆版本的复合外键。

记忆版本、快照项、依据和状态转换均禁止物理删除，外键删除操作设为 `RESTRICT`。将版本的结构化内容规范化为稳定顺序的 JSON，并计算 SHA-256 作为 `content_hash`，在保存前与读取时重新验证。SQLite 连接必须启用 `PRAGMA foreign_keys=ON`。

审查运行新增可为空的 memory_snapshot_id，以便构建过记忆上下文的审查能够引用使用的快照。

M2 的主要表作为 0002 前向迁移添加，审查运行对记忆快照的引用列作为 0003 前向迁移添加。禁止修改已共享的 M1 迁移。

评估匹配为人工裁定保存盲审令牌、裁定理由、裁定时间和排除统计标记。
每个未裁定项的盲审令牌唯一，裁定人员看不到比较组、模型及是否使用记忆。
如果裁定后的匹配关联到已知问题，在同一事务中排除同一评估中的旧假阴性并重新计算精确率、召回率、
严重问题召回率、重复数与未裁定数。保留原记录供审计。
上述审计列及盲审令牌索引在 0004 前向迁移中添加。
同一迁移保存评估与评估期间执行的所有审查运行之间的关联。即使审查发现为 0 也保留关联，
且禁止从以 Test 正确答案数据运行的审查所获反馈中提取记忆候选。
保存无问题变更以供评估的 `ground_truth_cases` 在 0005 前向迁移中添加。
既有数据库依据 `ground_truth_issues` 的变更引用补全用例。

## 11. 正确答案数据

候选来源包括人工审查、修复提交、测试和故障、静态分析与 `MISSED_ISSUE`。由创建者之外的审查人员验证，由维护人员批准。

发布数据集时只选择已批准的用例和问题，按稳定顺序排列拉取请求、提交和问题，生成 `set_hash` 并固定为不可变的 `PUBLISHED` 状态。无问题的用例也纳入哈希。订正通过发布新版本处理。

用于生成候选的辅助目录支持在各问题上选填 `sequence`，以便在保留现有编号的同时为同一变更添加其他根因。
未指定时按原有枚举顺序编号。在创建输出位置前，验证最终编号为正整数、在整个集合中唯一且从 1 连续递增，
并在候选 JSON 中按编号输出。此扩展只涉及生成输入，正式发布 JSON 的模式版本 2 和现有已发布数据集保持原样。

发布输入采用拒绝附加字段的严格 JSON，验证创建者和验证者分离、批准者、位置、依据及集合内序号的唯一性。
模式版本 2 要求 `cases`，用例变更引用必须唯一，每个问题的变更引用也必须在用例中存在。
输入文件及数据库均限制在仓库内，仅有正确答案数据发布权限的维护人员可操作。

测试数据集须包含至少 20 个拉取请求（包括无问题的用例）、至少 30 个问题，且至少 5 个严重问题分布在至少 3 个拉取请求中，才可判定成功。

## 12. 审查发现匹配与评估

自动匹配以同一拉取请求、根因、兼容的问题类型或规则 ID，以及路径加行号或符号为条件。
候选为 0 个或多个时标记为 `REVIEW_REQUIRED`，并对裁定人员隐藏比较组。

若多条审查发现匹配同一条正确答案，首条归为 TP，其余同时计为重复及 FP。参考审查发现不计为检出。

所有组使用相同的模型、提示词、规则快照、测试数据集、采样及用例顺序，只有 C 组增加记忆快照。
每个比较组与用例的组合至少运行 3 次。

匹配审查发现前，确认所有纳入评估的审查运行均为 `SUCCESS`。

任意运行处于 `FAILED`、`PARTIAL_SUCCESS`、`BLOCKED` 或未完成状态时，不得将失败运行按 0 条审查发现计分，
将评估整体设为 `INCOMPLETE_REVIEW_RUNS`。在检查完成之前，将所有比较组及重复运行的报告保留在内存中。
不完整时禁止保存任何比较指标、匹配结果、推荐及判定候选。仅在重新运行后所有目标审查均达到 `SUCCESS` 时，
才保存报告并确定比较结果。

保存 TP/FP/FN、精确率、召回率、严重问题召回率和保留率、重复数、无效率、Token、等待时间与费用及分子和分母。
除数为 0 时标记 `NOT_EVALUABLE`。成功判定实施概要设计 15.6，并验证严重问题 ID 集合的包含关系。

严重问题保留判定以 B 组任一重复运行检出的严重问题 ID 的并集为总体，要求 C 组每次重复运行检出 ID 的交集包含该并集。
B 组某次未检出，不能据此将已检出的严重问题排除出总体。
只有 B 组全部重复运行均未检出严重问题时，才将保留率标记为 `CRITICAL_RETENTION_NOT_EVALUABLE`。

任意比较组或重复运行仍有未裁定匹配时，返回原因代码 ADJUDICATION_REQUIRED，不得判定 MVP 成功。
未裁定数量保存于各组报告和评估测量数据。

### 15.2 覆盖率验收标准

M2 与 M1 相同，要求语句覆盖率和分支覆盖率均为 100%。

| 指标 | 必需值 | 判定 |
|---|---:|---|
| M2 单元测试范围的语句覆盖率（C0） | 100% | 所有可执行语句至少验证一次 |
| M2 单元测试范围的分支覆盖率（C1） | 100% | 验证条件、短路求值、异常及重试的全部路径 |
| M1＋M2 整体语句覆盖率（C0） | 100% | 合并单元、契约、集成与 E2E 测试后，未执行语句数为 0 |
| M1＋M2 整体分支覆盖率（C1） | 100% | 部分覆盖的分支数为 0 |
| 测试通过率 | 100% | 无失败及无理由的 skip 或 xfail |

标准执行命令如下。

~~~bash
uv run --frozen pytest tests/unit -q

uv run --frozen pytest -q \
  --cov=self_improving_code_review \
  --cov-branch \
  --cov-report=term-missing \
  --cov-report=xml:coverage.xml \
  --cov-fail-under=100
~~~

原则上禁止使用 `# pragma: no cover` 或 Coverage 的 `omit`、`exclude_lines` 排除。
存在不可到达的防御代码时，应将其调整为可到达的契约，或在设计审查中批准排除理由、目标行、
替代验证和质量影响。确认 C0 及 C1 的实际值均为 100%，禁止以四舍五入后的显示值作为依据。
