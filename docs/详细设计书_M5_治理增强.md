# M5 详细设计书：治理和扩展性

## 1. 目的与范围

M5 保持 M1～M4 的外部契约，实现记忆生命周期、项目隔离、可观测性、专项审查人员和故障恢复。
范围外包括自动审批、额外训练、向量数据库、固定启动所有审查人员、自动路由到多个模型、Webhook、Web UI、Kubernetes 和实际迁移到外部数据库。

M5 新增功能默认禁用，沿用 M1～M4 的配置和结果。正式使用前必须注册项目、配置权限、在迁移前备份并显式启用各功能开关。
TBD-06 的生产审批方式解决前，治理操作限于 `is_production: false` 环境下的允许列表方式。

## 2. 记忆治理

新增 `supersede`、`archive`、`restore-as-new-version` 和 `resolve-conflict` 操作。
每次内容更新均新增版本，并记录状态转换。

冲突情形包括：

- 同一适用范围内的事实互相矛盾
- 同一问题类型的 `suppress` 和 `reinforce` 冲突
- 框架或版本条件重叠
- 证据来源失效或撤回

`ConflictDetector` 提供冲突候选，维护人员从 `NARROW_SCOPE`、`SUPERSEDE_LEFT`、`SUPERSEDE_RIGHT` 和 `REJECT_CANDIDATE` 中选择。判定理由和证据必填。

归档后从后续快照排除并保留历史。恢复创建状态为 `PENDING` 的新版本，须重新审批。

## 3. 失效与重新验证

在记忆版本上新增 `valid_from`、`review_after` 和 `framework_version_constraints`，
在记忆主体上新增 `last_confirmed_at`。
到期由 `memory_revalidations.status=due` 表示，沿用已有 `MemoryStatus`。
到期版本从检索和新快照排除。重新确认时创建并启用下一版本，禁止覆盖先前版本内容。

## 4. 多项目

所有聚合与检索必须以 `project_id` 作为分区键。使用 `project_repositories` 关联仓库外部 ID 和项目，禁止在多个项目间隐式共享同一仓库。

应用启动时确定项目上下文。检索仓库、记忆、规则和正确答案数据时必须确认归属一致。
跨项目 ID 引用返回 `NOT_FOUND`，避免泄露资源是否存在。

## 5. 专项审查人员

审查人员注册表：

| 配置档案 | 启动条件 | 必查项 |
|---|---|---|
| GENERAL | 默认 | 正确性、可维护性 |
| SECURITY | 认证、SQL、命令、敏感信息 | 注入、授权、泄漏 |
| DATA | 迁移、Schema、事务 | 一致性、兼容性 |
| TEST | 测试变更或生产代码变更 | 回归、失败路径 |

以 M3 的单审查人员计划为基准，仅在 M5 启用后通过确定性风险判定增加 0～1 位辅助审查人员。
计划最多包含 2 位审查人员，禁止使用 LLM 进行选择。
每位审查人员使用同一固定差异和规则集合，但须按各自提示词重新构建发送内容并在发送前检查敏感信息。
将结果转换到共用发现 Schema，以不依赖审查人员的指纹合并。

禁止固定启动所有审查人员。仅当辅助审查人员对应的预计风险达到配置阈值时启用。
按配置档案统计 Token 和有效发现。

## 6. 可观测性

为共用遥测端口实现 OpenTelemetry 适配器。

跟踪结构：

~~~text
review.run
├── change.acquire
├── review.bundle
│   ├── secret.scan
│   ├── llm.generate
│   ├── context.tool
│   ├── llm.reflect
│   └── finding.validate
└── persistence.finalize
~~~

属性仅允许 ID、状态、提供方、模型、Token、延迟、费用和数量。
禁止将输入来源、差异、提示词、反馈正文或敏感信息候选写入 span 或事件。

度量值包括：

- 运行成功、部分成功、失败和阻断率
- LLM 错误、超时和 Schema 非法
- 无效位置和证据
- Token、费用、延迟
- 记忆命中、截断、冲突和评审期限到期
- 各审查人员配置档案的有效发现
- SCM 发帖失败

## 7. 扩展性与并发

SQLite 运行时使用进程内单写入协调、WAL 和 busy timeout。
读取使用短生命周期连接，禁止长事务。迁移到外部数据库超出 M5 范围。
度量值超过配置阈值时保持现有数据库端口，并记录为后续阶段决策事项。

工作线程持有执行租约，通过 `lease_owner`、`lease_expires_at` 和心跳防止重复执行。租约到期后重新获取，从检查点恢复。

## 8. 新增 Schema

| 表或列 | 内容 |
|---|---|
| `projects` | 项目 ID、名称、策略哈希、状态、乐观锁版本 |
| `project_repositories` | 项目与仓库外部 ID 的唯一对应 |
| `project_ground_truth_sets` / `project_scm_changes` | 现有聚合的项目归属 |
| `memory_conflicts` / `memory_relations` | 冲突、解决、替换和恢复的不可变引用 |
| `memory_revalidations` | 目标版本、期限、判定、操作者、证据哈希 |
| `reviewer_executions` | 审查单元、审查人员、启动原因、状态、用量 |
| `reviewer_finding_sources` | 合并后的发现与各审查人员原始发现的对应 |
| `run_leases` | 运行、所有者、期限、心跳、围栏令牌 |
| `memory_versions` / `memories` 新增列 | 生效时间、重新确认期限、版本约束、最终确认时间 |

`review_runs`、`memories`、`memory_extraction_runs` 和 `memory_snapshots` 已有 `project_id`。
M5 分阶段迁移尚无项目标识的正确答案数据和 SCM 聚合。
现有行通过使用已配置 `project_id` 的显式迁移补齐。候选项目有多个时须失败，禁止自动猜测。
保留已共享的 0001～0008，使用 0009 起的前向迁移，并在迁移前备份。

## 9. 运维

- 仪表盘仅显示已保存的度量值。引用原始输入时须按权限重新获取。
- 告警覆盖敏感信息阻断激增、严重问题保留率不达标、LLM 失败、数据库备份失败和 SCM 发帖失败。
- 备份恢复测试须验证记忆证据链、快照、规则引用和评估结果。
- 归档损坏的记忆并保留历史。

验证状态转换属性、项目隔离、冲突解决、到期复核、审查人员选择、跨审查人员去重、
遥测敏感信息排除、租约竞争和备份恢复。

## 12. 配置契约

~~~yaml
governance:
  enabled: false
  memory_lifecycle_enabled: false
  specialized_reviewers_enabled: false
  execution_leases_enabled: false
  max_reviewer_profiles: 2
  additional_reviewer_risk_threshold: high
  specialist_total_tokens: 6000
  specialist_max_output_tokens: 3000
  revalidation_default_days: 180
  lease_seconds: 180
  heartbeat_seconds: 30
  sqlite_busy_timeout_ms: 5000
telemetry:
  enabled: false
  provider: noop
  endpoint: null
  allowed_hosts: []
  service_name: self-improving-code-review
  sample_ratio: 0.0
  export_timeout_seconds: 5
  max_queue_size: 2048
~~~

- `governance.enabled=false` 时保持 M1～M4 的行为。此状态下不得在配置中启用其子功能。
  启用前准备所需的 `project register`、`bind-repository`、`adopt-existing` 和 `backup verify` 可以独立于审查流程执行。
- `max_reviewer_profiles` 为 1～2，仅使用辅助审查人员时才设为 2。
- `specialist_total_tokens` 是所有审查人员共用的追加预算，禁止简单相加各人的预算。
- `heartbeat_seconds` 不得大于 `lease_seconds / 3`。
- `lease_seconds` 至少是 LLM 与 SCM 超时中的较大值加 30 秒。
- `telemetry.enabled=true` 时必须设置 `provider=opentelemetry`、发送端点和端点允许列表。
- `telemetry.enabled=false` 时设置 `provider=noop`，不加载端点或凭据。
- OpenTelemetry 端点须为 HTTPS，禁止包含用户信息、查询参数或片段，且须与 `allowed_hosts` 完全一致。
- OpenTelemetry 认证请求头仅从环境变量获取，禁止保存到配置、数据库或日志。
- 认证请求头固定从 `REVIEW_OTEL_EXPORTER_HEADERS` 读取，禁止在配置中直接指定值。
- 将规范化后完整配置的哈希用于审计。
  `pipeline_config_hash` 包含会影响评审结果的项目策略、审查人员选择、预算和提示词哈希。
  遥测端点、采样率、队列设置、租约时间及 SCM 发帖门禁等运维值排除在该哈希之外。
- 恢复时须重新验证 `pipeline_config_hash`、审查人员计划、审查人员提示词及固定输入。

## 13. 项目上下文与隔离

### 13.1 确定步骤

1. 将 CLI 显式值或配置中的 `project_id` 验证为 `ProjectId`。
2. 在 `projects` 中精确查找有效项目。
3. 用 `RepositoryIdentityResolver` 确定目标仓库标识。
4. 确认 `project_repositories` 的映射具有相同的 `project_id`。
5. 将 `ProjectContext` 作为必填参数传给数据库仓储。

本地标识优先使用规范化的 Git 远端外部 ID。没有远端时，将规范化绝对路径的 SHA-256 表示为 `local:<hash>`。
禁止把原始绝对路径保存到数据库、日志或遥测。拒绝把同一外部仓库注册到多个项目。

### 13.2 检索边界

- 查找记忆、正确答案数据、评估、SCM 变更请求和同步游标时先核对项目归属。
- 下层 ID 存在但属于其他项目时返回 `NOT_FOUND`，不透露所属项目。
- 现有带 `review_runs.project_id` 的聚合从父运行确定归属，无需新增重复列。
- 规则快照可共享不可变内容。根据所属运行判定引用权限。
- 项目归档后只允许查阅历史，拒绝新运行和治理操作。

启用 M5 时，评估、发布正确答案数据、人工裁定、SCM 评审与反馈同步 CLI 在启动时验证项目上下文，
然后将已验证的 `ProjectId` 传入 `EvaluationStore`、SCM 发布存储及 SCM 反馈存储。
正确答案集合和 SCM 变更请求检索、评估报告、人工裁定、发布计划、同步游标和反馈目标均必须与映射表完全一致。
新建正确答案集合或 SCM 变更请求时，在同一事务保存主体及归属。归属保存失败时主体也回滚。
缺少归属的现有资源在显式迁移前一律返回 `NOT_FOUND`。

## 14. 记忆治理细节

### 14.1 允许的状态转换

| 原状态 | 操作 | 目标状态 | 内容版本 |
|---|---|---|---|
| `pending` | 审批 | `active` 或 `conflict` | 仅范围变更时创建下一版本 |
| `pending` | 驳回 | `rejected` | 不变 |
| `conflict` | 缩小范围 | `active` 或 `conflict` | 下一版本 |
| `conflict` | 驳回候选 | `rejected` | 不变 |
| `active` | 替换 | `superseded` | 用独立引用固定替换目标 |
| `active` | 归档 | `archived` | 不变 |
| `archived` | 恢复为新版本 | `pending` | 下一版本 |

`rejected` 和 `superseded` 为终态，禁止直接恢复。
禁止物理删除旧版本、转换、证据、冲突和替换关系。
全部更新须带 `expected_lock_version`。发生竞争时以 `ConcurrencyConflictError` 失败。

### 14.2 冲突解决

`memory_conflicts` 固定左侧和右侧的记忆 ID 及版本、原因代码和检出时的内容哈希。
每次解决选择以下一项。

| 解决值 | 处理 |
|---|---|
| `narrow-scope` | 创建缩小候选范围的下一版本，重新检查剩余冲突 |
| `supersede-left` | 将左侧设为已替换，启用右侧 |
| `supersede-right` | 将右侧设为已替换，启用左侧 |
| `reject-candidate` | 驳回候选，保留现有有效版本 |

在一个短事务内完成两侧状态变更、关系记录和冲突结案。
冲突检出、方案选择和撰写理由由确定性代码与人员完成，禁止使用 LLM。
须记录解决人、理由、证据摘要以及解决前后的内容哈希。

### 14.3 失效与重新验证

- `valid_from` 和 `review_after` 使用 UTC，且必须满足 `valid_from < review_after`。
- 到期判定仅依赖注入的 `Clock`，无需后台常驻处理。
- 即便是 `active`，满足 `review_after <= now` 的版本也从新检索和新快照中排除。
- 已有快照继续用于复现过去运行。
- 重新确认时复制相同内容形成下一版本，并更新确认时间与下次到期时间。
- 判定失效时将当前版本设为 `archived`，把理由和证据保存在 `memory_revalidations`。
- 将框架约束验证为按名称指定的 PEP 440 版本说明符。运行侧版本未知时跳过带约束的记忆并记录 `FRAMEWORK_VERSION_UNKNOWN`。

## 15. 专项审查人员

### 15.1 确定性选择

始终保留一位 M3 选定的主审查人员。
M5 按以下顺序为辅助评审候选打分，只加入达到阈值的最高分候选。同分优先顺序为 `security > data > test`。

| 辅助审查人员 | 主要判定条件 | 原因代码示例 |
|---|---|---|
| `security` | 认证、授权、SQL、命令、秘密、危险序列化、重大风险 | `SECURITY_BOUNDARY` |
| `data` | 迁移、Schema、持久化、事务、兼容性 | `DATA_INTEGRITY` |
| `test` | 实现与测试同时变更、仅测试、失败路径规则 | `TEST_COVERAGE` |

评分仅使用文件路径、变更类型、风险和适用规则分类。禁止把差异正文交给 LLM 选人。
命中路径或规则分类计 3 分，同时变更测试和实现计 2 分。
重大风险的 3 分适用于数据类和测试类路径以外的变更，避免把迁移及测试变更误分给安全审查人员。
阈值 `low/medium/high` 分别为 1/2/3 分。计划哈希包括选择结果、原因代码、得分和预算排除原因。

包含专项审查人员的公开结果采用 `schema_version=2`。
`reviewer_metrics` 返回按人划分的安全汇总值，包括输入和输出 Token、延迟、费用、有效发现数和重复数。

### 15.2 执行与合并

- 初版在同一审查单元内按稳定顺序串行运行各审查人员，只在审查单元之间并行。
- 在 `reviewer_executions` 分别保存各审查人员的调用键、提示词版本、用量及状态。
- 将审查人员提示词版本化存放于 `prompts/review_specialist_v1.yaml`，采用 4 项的闭合列表。
- `DatasetLlmClient` 的调用键含运行、审查单元、审查人员、轮次和调用类型。
- 全部审查人员通过共同的闭合输出 Schema 及确定性位置、证据验证。
- 使用不含审查人员名称的现有指纹去重，在独立表中保存全部来源。
- 依次按严重程度、证据验证结果、审查人员优先级、发现 ID 确定性选出同一发现的显示值。
- 即使仅辅助审查人员失败，也将运行标记为 `partial-success`。M4 仍仅允许成功时发帖。
- 按配置档案统计输入和输出 Token、延迟、费用、有效发现数和重复数。

## 16. 遥测

### 16.1 端口

在应用层定义 `Telemetry` 端口，提供 `start_span`、`add_event`、`record_counter` 和 `record_histogram`。
默认实现为 `NoopTelemetry`，禁止将 OpenTelemetry SDK 类型暴露给应用层、领域层和 JSON 输出。
OpenTelemetry SDK 和导出逻辑限于 `infrastructure/telemetry/` 及可选依赖组。
选择 `provider=opentelemetry` 但缺少依赖时，以安全的配置错误中止启动。禁止隐式切换到 `NoopTelemetry`。

### 16.2 属性允许列表

仅允许以下属性。

```text
run_id / bundle_id / project_id / status / error_code
model / prompt_version / reviewer_profile / provider
input_tokens / output_tokens / duration_ms / retry_count
finding_count / valid_finding_count / duplicate_count / blocked_count
```

禁止以下值：差异、代码、路径、符号、规则正文、记忆正文、反馈理由、提示词、工具结果、
敏感信息候选、HTTP 正文、凭据及本地绝对路径。
属性名也按允许列表检查，并限制字符串长度和属性数量。

### 16.3 故障契约

- 端点或配置无效时在启动阶段失败。
- 运行中导出失败时保持评审结果，只记录安全错误代码和丢弃数量。
- 队列设上限，退出时的刷写时间不得超过 `export_timeout_seconds`。
- 常规测试使用 `NoopTelemetry` 或记录用伪实现，禁止发送到外部。
- 禁止将跟踪采样结果用于业务处理、状态转换或判断是否可恢复。

### 16.4 实现状态

共用端口、Noop、安全边界和通过 OTLP/HTTP 导出跟踪及度量值均已实现。
观测 `review.run`、`change.acquire`、`review.bundle`、`secret.scan`、`llm.generate`、
`context.tool`、`llm.reflect`、`finding.validate`、`persistence.finalize`，
记录整个运行及各审查人员的 Token、延迟、费用、有效发现数和重复数。
将 OTLP 的共用端点确定性规范化为 `/v1/traces` 和 `/v1/metrics`。

## 17. 执行租约与 SQLite

### 17.1 租约契约

`run_leases` 按 `run_id` 保存所有者、期限、心跳时间及单调递增的 `fencing_token`。
通过带条件的单条 SQL 和短事务取得、更新或释放租约。

- 只有尚未获取或已经到期时才可获取。
- 心跳和完成更新要求所有者与 `fencing_token` 均匹配。
- 外部 LLM、SCM 及 OpenTelemetry 调用期间不得持有业务事务。
- 专用心跳逻辑仅使用短连接，在外部调用期间续期。
- 失去租约后停止当前处理，不再保存外部应答，由重新获取者接手。
- 重新获取者必须重新验证 M3 输入、计划、各单元及上下文来源哈希，再恢复运行。
- 时间、所有者 ID 和执行心跳的逻辑可注入。

### 17.2 SQLite 配置

- 每个连接应用 `foreign_keys=ON`、`journal_mode=WAL` 及已配置的 `busy_timeout`。
- 写入通过进程内协调，进程间正确性由唯一约束和租约保证。
- 仅在上限内重试 `database is locked`，禁止对其他 SQL 错误重试。
- WAL 检查点及备份与运行中的外部调用分离。

### 17.3 实现状态

评审开始时取得执行租约，外部调用期间通过独立短连接定期发送心跳。
恢复运行采用同一契约。保存前重新验证所有者和围栏令牌。
最终状态更新与租约释放在同一事务内通过带条件的 SQL 完成。租约到期且已被重新获取时，拒绝保存旧所有者结果。
同一幂等键的并发首次启动也转换为并发运行冲突。

SQLite 的普通工作单元和租约专用连接都应用 WAL、外键检查和已配置的 `busy_timeout`。
租约专用写入仅对 `database is locked` 执行有上限的重试，其他 SQL 错误转换为项目异常并直接返回。
测试可替换时间、所有者 ID 和心跳执行逻辑。

## 18. CLI 契约

| 命令 | 主要必填输入 | 功能 |
|---|---|---|
| `review governance project register` | `--project --name --actor --reason` | 注册项目 |
| `review governance project bind-repository` | `--project --provider --external-repository --actor --reason` | 唯一绑定仓库 |
| `review governance project list` | `--config` | 显示无正文的注册信息 |
| `review governance project adopt-existing` | `--project --resource-type --resource-id --actor --reason` | 逐项显式关联无归属的现有资源 |
| `review memory archive` | `MEMORY_ID --project --lock-version --actor --reason` | 归档有效记忆 |
| `review memory restore` | `MEMORY_ID --project --lock-version --actor --reason` | 从归档版本创建待审批的下一版本 |
| `review memory supersede` | `MEMORY_ID --replacement --project --lock-version --actor --reason` | 记录替换关系 |
| `review memory conflict list` | `--project --status` | 显示冲突标识及原因代码 |
| `review memory conflict resolve` | `CONFLICT_ID --resolution --lock-version --actor --reason --evidence` | 人工解决冲突 |
| `review memory revalidation list` | `--project` | 显示到期记忆 |
| `review memory revalidation confirm` | `MEMORY_ID --project --lock-version --actor --reason --evidence` | 启用重新确认并具有默认期限的下一版本 |
| `review memory revalidation invalidate` | `MEMORY_ID --project --lock-version --actor --reason --evidence` | 使记忆失效并归档 |
| `review governance backup verify` | `--database --project --actor --output` | 以只读方式验证恢复后数据库的一致性 |

共用的 `--repository`、`--config`、`--output` 沿用现有契约。面向用户的说明以简体中文集中在 `messages.py`。
成功退出码为 0，非法输入为 1，现有共用异常遵循共用退出码。
乐观锁或租约竞争以安全的 `CONCURRENCY_CONFLICT` 返回退出码 5。
JSON 默认返回 ID、状态、版本、原因代码和内容哈希，隐藏原始正文、理由和证据。
备份验证正常时返回 0。不一致时保存安全的验证报告并返回 5。
报告只包含检查项名称、布尔值、失败原因代码和目标项目的汇总数量，禁止包含数据库路径、SQL 或行内容。

## 19. 持久化与迁移

### 19.1 前向迁移

| 迁移 | 内容 |
|---|---|
| `0009_m5_projects.sql` | `projects`、`project_repositories`、`project_ground_truth_sets`、`project_scm_changes` |
| `0010_m5_memory_governance.sql` | 版本期限列、`memory_conflicts`、`memory_relations`、`memory_revalidations` |
| `0011_m5_reviewers_leases.sql` | `reviewer_executions`、`reviewer_finding_sources`、`run_leases` |

在映射表为无项目标识的现有正确答案集合和 SCM 变更请求增加归属。
启用 M5 前，按资源 ID 逐项执行 `review governance project adopt-existing` 显式配置归属。
`resource-type` 采用由 `ground-truth-set` 和 `scm-change` 组成的闭合列表。
禁止批量猜测或自动接纳所有资源。
缺少映射或存在多个映射时拒绝启动评审，对应的治理命令仍可运行。
在同一事务内创建新聚合的主体和映射。

### 19.2 主要约束

- `projects(project_id)` 为主键，状态限于 `active/archived`。
- `project_repositories(provider, repository_external_id)` 全局唯一。
- 项目映射表中的资源 ID 仅能属于一个项目。
- `memory_conflicts` 将左右两侧按规范顺序排列，确保同一未解决组合唯一。
- `memory_relations` 保存替换源、替换目标和关系类型的不可变引用。
- `reviewer_executions(run_id, bundle_id, profile)` 唯一。
- `reviewer_finding_sources` 关联合并后发现和各审查人员的所有原始发现。
- `run_leases.run_id` 唯一，`fencing_token >= 1`。
- 金额保存为 `TEXT` 十进制数，时间保存为 UTC ISO 8601，枚举值使用小写 kebab-case。

迁移前获取 SQLite 在线备份。应用后验证 `integrity_check`、外键、数量、项目映射、记忆内容哈希及快照哈希。
禁止修改已共享迁移、执行破坏性自动回滚或物理删除历史行。

### 19.3 备份验证

- 通过 SQLite URI 的 `mode=ro` 打开目标数据库并启用 `query_only`。禁止初始化或执行迁移。
- 检查 `integrity_check`、外键、必需 M5 表及指定项目是否存在。
- 检查正确答案集合、SCM 变更请求、评审、记忆、提取、冲突及重新验证是否缺少归属。
- 重新计算记忆内容哈希、记忆和规则快照的条目及集合哈希，以及固定在审查运行中的规则哈希。
- 检查读取所有行，对外仅返回安全的布尔值、失败原因代码和汇总数量。
- 当前 CLI 的验证目标限于规范化后仍在仓库内的普通文件。将来如允许仓库外路径，须另行设计显式只读允许列表。

## 20. 事务与幂等性

- 项目注册键为 `project_id`，仓库映射键为提供方和外部 ID。
- 治理操作键包含操作、记忆 ID、目标版本、期望锁版本、操作者和规范化理由哈希。
- 重新验证键包含记忆 ID、目标版本、结果、下一期限和操作者。
- 审查人员运行键包含运行 ID、审查单元 ID、审查人员、其提示词哈希和输入哈希。
- 冲突解决、两侧状态转换及替换关系在同一工作单元内确认。
- 遥测发送、LLM 和 SCM 调用期间禁止持有数据库事务。
- 相同操作已经完成时返回现有结果，禁止重复创建正文或审计行。

## 21. 安全与审计

- 为每种新治理操作分别增加 `Permission`，通过授权端口核对权限。CLI 的 `--actor` 仅表示请求中的操作者。
- 分离 `manage-project`、`govern-memory`、`revalidate-memory` 和 `verify-backup`。
- 检查理由及证据的长度、控制字符和敏感信息。禁止将原始值写入日志、遥测或异常。
- 拒绝跨项目引用、任意数据库路径、任意 OpenTelemetry 端点和未注册审查人员。
- 备份验证目标限于当前仓库。若将来支持外部路径，也须限定为显式配置的只读允许列表。
- OpenTelemetry 和备份验证失败信息禁止包含完整 SQL、行内容和认证请求头。
- 审计记录保存操作者、操作、目标 ID、目标版本、前后状态、理由哈希和时间。
