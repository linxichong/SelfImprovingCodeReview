# デモ想定問答

[デモ手順](デモ手順.md)に沿って説明するときの質問と回答。各回答の冒頭で要点を伝え、必要に応じて実装や確認結果を示す。

## 仕組みとコンテキスト

### Q01. このツールは何をするのか

Git 差分を LLM にレビューさせ、候補の位置・根拠・ルール参照をプログラムで検証して保存する。GitHub デモでは、検証済みの指摘を PR に投稿し、人のフィードバックから作った知識候補を承認後のレビューで再利用する。 [レビュー実行フロー](概要设计书.md#71-コードレビュー実行フロー)

### Q02. Codex の Skill とレビュー用プロンプトはどう関係するか

`SKILL.md` は既存の `review` CLI を呼び出す手順。レビュー先の LLM に送るシステム指示は `prompts/` の版管理済み YAML から作る。VS Code では Skill がフィードバック提出と知識承認の人間確認を挟んで再レビューまで進める。GitHub の投稿と返信同期の実演では `review scm review` と関連コマンドを Bash で実行する。 [Skill](../.agents/skills/self-improving-code-review/SKILL.md) · [デモ手順](デモ手順.md)

### Q03. LLM へ一回に何を渡すのか

レビュー単位ごとに `system` と `user` の二つのメッセージを作る。`system` は版管理済みのレビュー指示。`user` は単位 ID、視点、リスク、ファイル一覧、JSON 応答スキーマ、適用ルール、選択された知識、ファイル別の変更メタデータ、その単位の差分の順に組み立てる。メタデータには実際に送るルールの ID をファイルごとに含める。 [テンプレート](../prompts/review_general_v1.yaml) · [要求組み立て](../src/self_improving_code_review/application/review/context_builder.py)

### Q04. 同じ PR にある文書は、コードのレビューにも見えるか

初回に見える差分は、そのコードと同じレビュー単位に入ったもの。PR では `base...head` の差分を取得し、対象ファイルの関係とトークン予算で単位を分ける。デモ PR #1 の診断では `docs/email-lookup.md` が `B001`、`src/order_repository.py` が `B002` だった。動的コンテキストが無効な現行デモでは、`B002` の要求に `B001` の文書差分は入らない。 [診断の仕様](详细设计书_M1_审查基础.md#7-ルールと実行計画) · [単位分割](../src/self_improving_code_review/application/review/bundler.py)

### Q05. 追加の仕様書はどう読むのか

`review.context_tools_enabled` を有効にすると、モデルは `tool-request` でファイルの行範囲、シンボル、文字列検索などを要求できる。PR の場合は固定した Git リビジョンの許可済み UTF-8 ファイルを対象とし、パス、サイズ、予算、機密情報を検査してから、結果を同じ単位の次のターンに追加する。Git 管理された Markdown は候補になる。外部の文書サービスや PDF をこの機能で直接取り込むことはできない。 [コンテキスト取得契約](详细设计书_M3_流水线增强.md#7-コンテキスト取得契約) · [ツールループ](详细设计书_M3_流水线增强.md#9-エージェントツールループ)

### Q06. LLM の行番号や回答をそのまま使うのか

プログラムが応答スキーマ、差分内の位置、根拠の原文一致、ルールの適用先を検査する。根拠の引用から差分上の位置を特定できる場合は、その位置を使う。検証を通った主要指摘を `findings` に出し、追加情報が必要な参照候補は `reference_findings` に分ける。これらの検査は、提供されていない業務仕様の正しさまで保証するものではない。 [検証と結果分類](../src/self_improving_code_review/application/review/review_manager.py)

### Q07. コードや業務資料を外部 LLM に送る場合、どう守るのか

外部送信を明示的に許可した構成で、現在の単位の差分、適用ルール、選択された知識、必要な追加断片に範囲を絞る。送信前の機密検査で検出した場合はレビューを `BLOCKED` にする。差分とツール結果は未信頼データとして境界で囲む。追跡用には版、ハッシュ、使用量などを記録し、完全なプロンプトや未加工応答は保存しない。 [送信範囲と信頼境界](概要设计书.md#14-セキュリティ設計概要)

### Q08. オンラインとオフラインの違いは何か

`ai_gateway` は明示したモデルで実 LLM を呼び出す。`dataset` は固定応答で、要求構築、検証、保存などを確認できる。固定応答で指摘が 0 件でも、実コードに問題がないという確認には使えない。 [ローカル開発](../README.md#ローカル開発llm-トークン消費なし) · [外部 LLM の設定](../README.md#実際の-ai-ゲートウェイを使用する場合)

## 業務レビューと知識の再利用

### Q09. 実行できるコードでも、業務仕様に反していれば指摘できるか

業務上の期待動作をルールや根拠資料として渡せば、仕様違反もレビューできる。デモ用の `demo/missing-order` には、存在しない注文の応答を `404` から `200` に変える例がある。プロジェクトルール `ORDER.API.NOT_FOUND` は `404` と `order_not_found` を要求する。固定差分で `review rules check` を実行し、`src/order_api.py` にそのルールが送信対象として選ばれることを確認済み。実 LLM がこの例を指摘するかは、この診断の確認範囲外。 [ルール診断](详细设计书_M1_审查基础.md#7-ルールと実行計画)

### Q10. 業務資料がないときはどうなるか

コードから変更された動作は説明できる。例えば `404` が `200` に変わったことは差分で分かるが、どちらが業務上正しいかは契約や根拠が必要。材料不足の候補は `needs_context` として扱える。指摘が 0 件の場合も、未提示の業務要件に適合したとは判断できない。 [根拠に関するプロンプト指示](../prompts/review_general_v1.yaml)

### Q11. プロジェクトルールとメモリはどう使い分けるか

正式な契約や必須の制約は、版管理されたプロジェクトルールとして定義する。過去のフィードバックから得た再利用可能な確認観点は、保守担当者が承認したメモリとして加える。ルールの適用先は言語・パス・キーワードと予算から決まり、メモリは同じプロジェクトの有効版から適用範囲に合うものを選ぶ。 [ルールと適用範囲](详细设计书_M1_审查基础.md#7-ルールと実行計画) · [メモリ検索](详细设计书_M2_反馈记忆.md#7-検索)

### Q12. 評価の A・B・C は何を比較するのか

| 比較群 | レビューモード | LLM に渡す主な内容 |
|---|---|---|
| A | `baseline` | 共通のレビュー指示と Git 差分 |
| B | `rules` | A の内容に、差分に適用されるプロジェクトルールを追加 |
| C | `memory` | B の内容に、差分に適用される承認済みの知識を追加 |

共通のレビュー指示は、差分から裏付けられる問題を報告し、追加行の原文を根拠として引用し、指定された JSON 形式で返すよう LLM に求める。例えば、SQL インジェクションは A でも指摘できる。「注文が見つからない場合は HTTP 404 を返す」というプロジェクト固有の契約は、B で追加するルールから伝える。 [既定のレビュープロンプト](../prompts/review_general_v1.yaml)

A と B の比較でプロジェクトルールの効果を、B と C の比較で承認済み知識を追加した効果を測る。本プロジェクトの主な評価は B と C の比較。デモの初回は `rules`、承認後は `--mode memory` で実行し、知識の注入には `memory.is_injection_enabled: true` が必要。 [要素別比較](概要设计书.md#154-要素別比較) · [モード一覧](../README.md#レビュー方式)

### Q13. 知識の再利用はモデルの追加学習なのか

承認した知識を版付きで SQLite に保管し、次の実行時に該当する内容をプロンプトへ追加する方式。知識は確認観点を補強するもので、差分の根拠、行番号、重大度を上書きできない。抑制方向の知識があっても重大なセキュリティ指摘は通常の検証を通す。 [メモリの適用](详细设计书_M2_反馈记忆.md#8-レビューへの適用)

### Q14. フィードバックの取り込みと知識の承認は別か

別の操作。同期は人の評価と理由を保存し、LLM が再利用可能な知識候補を抽出する。抽出に成功すると候補は `pending` になり、保守担当者が内容・根拠・適用範囲を確認して承認すると `active` になる。フィードバックを保存できても抽出は失敗し得るため、`processed_count` に加え `memory list --status pending` を確認する。 [抽出の実行境界](详细设计书_M2_反馈记忆.md#31-フィードバック保存と候補抽出の実行境界) · [承認手順](デモ手順.md#3-保守担当者が候補を確認して承認する)

### Q15. 承認済みの知識が使われたことは、どこで確認するか

再レビュー結果の `run.versions.memory_snapshot_id` を確認し、対応する `memory_snapshot_items` に期待した知識 ID と版があることを確認する。空のスナップショットも作られるため、ID の表示だけでは個別の知識が使われた証拠にならない。 [デモの確認コマンド](デモ手順.md#4-承認済みの知識で同じ-pr-を再レビューする)

### Q16. 同じ指摘が再レビューでも出たら、知識は役に立っていないのか

このデモでは、重大な SQL インジェクションを引き続き指摘しながら、承認した観点を使えたことを確認する。指摘の増減だけで効果は判定できない。精度を比較する場合は固定した正解データと同一モデル・設定で、ルールのみの B と知識ありの C を各ケースで 3 回以上比較する。見逃し、誤検知、重大問題 ID の維持、使用量や費用を確認し、未裁定の照合を解消する。 [評価条件](详细设计书_M2_反馈记忆.md#12-指摘照合と評価)

## GitHub デモでの操作と切り分け

### Q17. なぜコメントに `/review-feedback` を書くのか

評価ラベルと理由を明示して取り込むための、このプロジェクトの入力形式。デモの `true-positive` は「この指摘は妥当」という意味で、理由には確認した事実を書く。通常の会話や絵文字はそのまま残り、知識の取り込みは明示した返信から行う。GitHub コメントでボットを操作する方式には Kubernetes などの先例があり、具体的なコマンド書式は各連携が定める。 [フィードバック契約](详细设计书_M4_SCM集成.md#12-フィードバック契約) · [Kubernetes の例](https://kubernetes.io/docs/contribute/review/for-approvers/)

### Q18. なぜ投稿と返信に別のアカウントを使うのか

投稿役の `linxichong` はボットとして登録され、同期時に自身の返信は除外される。フィードバックは、設定の `feedback_actor_mapping` に登録した別の GitHub ログイン名から、ツールの公開済み行コメントへ返信する。同期コマンドの PAT は投稿役のものを使う。 [同期の実装](../src/self_improving_code_review/application/scm/sync_feedback.py) · [返信手順](デモ手順.md#2-github-の返信から外部-llm-で知識候補を作る)

### Q19. `fetched_count: 2`、`processed_count: 0` は成功か

同期の取得処理は完了したが、フィードバックは 0 件。元の行コメントと人の返信の二件が取得されても、返信者が未登録なら返信は `UNKNOWN_ACTOR` として除外される。現在のデモ回の設定に返信者を登録し、元の行コメントへ新しい返信を投稿してから同期する。取得済みの同じイベント ID は重複処理しない。 [同期の処理順](详细设计书_M4_SCM集成.md#92-フィードバック同期)

### Q20. 同じ PR に同じコマンドを実行すると LLM を再度呼ぶか

同じ SQLite に、同じ冪等性キーの成功結果があれば再利用する。キーにはプロジェクト、ローカルリポジトリ、先端 SHA、差分、モード、設定、モデル、プロンプト、ルールなどが含まれ、知識を使う場合は有効メモリの状態も含まれる。同じ `run_id` の成功結果を返した場合、表示される Token は保存済みの値。GitHub の PR 状態と SHA はその都度確認する。 [キーの定義](../src/self_improving_code_review/application/review/review_preparation.py) · [再実行の設計](详细设计书_M4_SCM集成.md#10-冪等性と再実行)

### Q21. ドライランが成功すれば投稿も成功したことになるか

ドライランはレビュー結果と投稿計画の確認まで。`--publish` を付けた実行では、設定とレビュー成功を検証し、先端 SHA の再確認を経て投稿する。投稿後は `run.status` に加え `scm.publications[].status` が `published` であることを見て、`external_comment_url` を開く。 [投稿処理順](详细设计书_M4_SCM集成.md#91-レビュー)

### Q22. `HTTP_403` や「開いている変更要求だけ」のエラーはどう見るか

`HTTP_403` は GitHub が投稿を拒否した状態。現在の WSL Bash の PAT が対象リポジトリを選択し、`Pull requests: Read and write` を持つことを確認する。「開いている変更要求だけ」は PR の状態検査で止まったことを示す。未マージの PR が `Closed` なら `Open` に戻して同じデモ回で再実行する。 [事前準備と投稿手順](デモ手順.md#事前準備) · [失敗分類](详细设计书_M4_SCM集成.md#16-失敗分類)

### Q23. コメントを手動で消したあと、同じデモをどうやり直すか

同じデモ回の SQLite に旧コメント ID が残るため、再投稿では既存コメントを更新しようとする。投稿からやり直す場合は、前回のデモ用コメントの状態を確認し、新しいデモ回と独立した SQLite を使う。中断から続ける場合は既存のデモ回 ID を選ぶ。PR は開いた状態で使う。 [デモ回の選択](デモ手順.md#デモ回を選ぶ)

### Q24. コマンドを実行する場所と `DEMO_REPO` はどこか

`uv run` は外側の SelfImprovingCodeReview のルートで実行する。`DEMO_REPO` は内側の `.review/github-demo/code-review-demo` にあるレビュー対象の Git クローン。`DEMO_CONFIG` と SQLite は選択したデモ回のディレクトリにある。認証情報は実行する Bash の環境変数で渡す。 [事前準備](デモ手順.md#事前準備)

## 適用範囲の変更と結果の読み方

### Q25. 承認済みの知識の適用範囲を後から狭めるには

すでに `active` の知識は、保守用設定で `memory archive` して利用対象から外し、`memory restore` で承認待ちの `pending` に戻す。`memory show` で復元後の `lock_version` を確認し、`memory approve --scope-file` で狭めた範囲を指定して承認する。`lock_version` は同時更新を検出するための値。初回の候補がすでに `pending` なら、そのまま範囲を指定して承認できる。 [承認手順](デモ手順.md#3-保守担当者が候補を確認して承認する)

### Q26. `pr-1-dry-run.json` と `pr-1-memory.json` の両方に Token があるのはなぜか

前者は `rules` モードの初回レビュー、後者は承認済み知識を選んで `memory` モードで実行した再レビューの結果。どちらもドライランで、LLM によるレビューと投稿計画の作成まで行う。JSON の `input_tokens` と `output_tokens` はそのレビューの使用量で、フィードバックから知識候補を抽出したときの使用量は別に記録する。 [初回レビュー](デモ手順.md#1-外部-llm-でレビューしgithub-に投稿する) · [再レビュー](デモ手順.md#4-承認済みの知識で同じ-pr-を再レビューする)

### Q27. `B001` は何か。なぜ結果 JSON に見当たらないのか

`B001` は第 1 レビュー単位の ID。デモ PR #1 では `B001` が `docs/email-lookup.md`、`B002` が `src/order_repository.py` を担当した。結果 JSON は `metrics.bundle_count` に単位数を、各指摘にその指摘の `bundle_id` を出す。この例では `B001` に指摘がないため、指摘一覧に見えるのは `B002` だけ。`B001` の LLM 使用量も合計に含まれ、内訳は SQLite の `llm_calls` で確認できる。 [出力項目](../src/self_improving_code_review/cli/output.py)

### Q28. 知識を使うと Token 消費は増えるのか

知識が選ばれるとその本文が入力に加わる。デモ回 `run-SrV3bx7M` では、同じ PR の SHA、モデル、設定で次の値を確認した。

| Token | 初回 `rules` | 再レビュー `memory` | 増加 |
|---|---:|---:|---:|
| 入力 | 3,577 | 3,719 | 142 |
| 出力 | 405 | 442 | 37 |
| 合計 | 3,982 | 4,161 | 179 |

入力の増加は、承認済み知識 1 件を使った `B002` に集中した。`B001` の入力はどちらも 1,740 Token。出力は指摘が同じ 1 件でも文章の長さで変わる。この例で確認できたのは知識の適用と使用量の差で、品質の比較には Q16 の評価条件を使う。 [適用の確認方法](デモ手順.md#4-承認済みの知識で同じ-pr-を再レビューする)

### Q29. 初回レビューの JSON で、デモではどの項目を見せるか

PR #1 の初回レビュー例では、SQL インジェクションの主要指摘が 1 件あり、GitHub の行コメントを 1 件計画した。

| 項目 | この実行の値 | 説明 |
|---|---|---|
| `run.status` / `run.mode` | `success` / `rules` | プロジェクトルールを使う B 群の条件でレビューが完了した。 |
| `run.versions.prompt_version` / `run.versions.memory_snapshot_id` | `review_general_v1@5` / `null` | 既定のレビュープロンプト第 5 版を使用した。`rules` モードなので、知識の注入は行っていない。 |
| `findings[0]` | `B002-F001`、13 行目、`critical` | 第 2 レビュー単位の主要指摘。`evidence.quote` に差分から引用したコードがあり、`suggestion` では SQL のプレースホルダーと別引数を使う修正を提案している。 |
| `findings[0].validation` | 位置と根拠は `valid`、自己検証は `reflection-skipped` | プログラムが、指摘位置が差分の追加行にあることと、引用が差分の原文に一致することを確認した。候補の根拠が結論を支えるかを追加で判定する LLM 自己検証は、この実行では無効だった。 |
| `metrics` | 2 単位、入力 3,577・出力 417 Token、候補 1 件、検証通過 1 件 | Token は全レビュー単位の合計。候補は LLM が提案した指摘で、`validation_pass_rate: 1.0` は、この実行で候補 1 件中 1 件が検証を通過したことを示す。 |
| `scm.dry_run` / `scm.plans` / `scm.publications` | `true` / 行コメント計画 1 件 / `[]` | `src/order_repository.py` の 13 行目にコメントを付ける計画。投稿結果は空で、ドライランは計画の出力まで行う。 |

画面では `evidence.quote`、`validation`、`scm.plans` の順に示すと、引用した根拠、プログラムの検証結果、GitHub の投稿予定位置をたどれる。 [JSON の出力項目](../src/self_improving_code_review/cli/output.py) · [初回レビュー手順](デモ手順.md#1-外部-llm-でレビューしgithub-に投稿する)
